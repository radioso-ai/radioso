# Agents and skills

Agents are the user-facing knowledge assistants in a workspace. Skills describe the product work Radioso can perform through stable contracts such as assistant chat, retrieval answer, document search, and MCP tools.

The key point is that skills are discoverable, but they are not executed through a generic skill endpoint. Callers still use the stable API, SDK, or MCP contract for the actual work.

## Relevant endpoints

```text
GET    /api/v1/agents
POST   /api/v1/agents
GET    /api/v1/agents/{agentId}
PUT    /api/v1/agents/{agentId}
POST   /api/v1/agents/{agentId}/assistant-logo
DELETE /api/v1/agents/{agentId}/assistant-logo
POST   /api/v1/agents/{agentId}/default
GET    /api/v1/skills
GET    /api/v1/skills/{skillName}
```

## Agents

Each workspace has a default agent. Chat calls use that agent when `agentId` is omitted.

Agents own:

- display name and logo
- custom instructions
- suggested-question behavior
- theme and greeting behavior
- whether retrieval is enabled
- source scope
- surface settings for authenticated chat, anonymous chat, and website embed

Retrieval settings remain workspace-level. If an agent has `retrievalEnabled: true`, assistant chat may use workspace retrieval and return citations. If `retrievalEnabled: false`, the agent answers through the direct assistant path and returns diagnostics with `retrievalInvoked: false`.

## Contact requests

An agent can offer a "contact a human" option in chat. It is off by default and turned on per agent with `contactRequestsEnabled`. When it is on, the assistant collects the visitor's email and message, then delivers the request out of band.

You configure where requests go with `contactRequestDelivery`:

- `recipientEmails`: up to 5 email addresses. Each is emailed a copy of the request. When the list is empty, Radioso falls back to the workspace owner.
- `webhook`: an optional `{ "url": "https://..." }`. When set, Radioso also POSTs the request to that URL. Email and webhook both fire when both are configured.

Example agent update fragment:

```json
{
  "contactRequestsEnabled": true,
  "contactRequestDelivery": {
    "recipientEmails": ["support@example.com", "ops@example.com"],
    "webhook": { "url": "https://example.com/hooks/contact" }
  }
}
```

### Webhook payload and signature

The webhook receives a JSON body:

```json
{
  "name": "Ada",
  "email": "ada@example.com",
  "message": "Please call me back.",
  "workspaceId": "...",
  "conversationId": "...",
  "requestId": "..."
}
```

Two headers let you verify the request:

- `X-Radioso-Signature`: a base64url HMAC-SHA256 of the raw request body.
- `X-Radioso-Timestamp`: the send time in epoch milliseconds.

The signing key is not the raw deployment secret. It is derived once from the deployment's `WORKSPACE_TOKEN_SECRET` so the secret itself never leaves the server:

```text
signingKey = HMAC_SHA256(WORKSPACE_TOKEN_SECRET, "radioso/contact-webhook-signature/v1")
expected   = base64url(HMAC_SHA256(signingKey, rawBody))
```

To verify, compute `expected` over the exact bytes you received and compare it to `X-Radioso-Signature` with a constant-time check. In practice, read the raw body before parsing it as JSON, because re-serializing can change the bytes and break the comparison.

## Skills

The skills catalog is read-only. It helps API, SDK, MCP, and assistant clients understand what work is available and which stable contract owns it.

For example, `retrieval.answer` points to the retrieval answer API and MCP grounded-answer tool. It does not require callers to switch to a generic `POST /skills/{name}/execute` contract.

Skill entries include:

- name and description
- optional display metadata, such as a UI title or icon hint
- availability
- contract references
- required capabilities
- diagnostic fields exposed by the implementation
- skill-owned outcomes, each mapped to a normalized status such as `completed` or `failed`

## Common failure modes

- `400` on agent create or update usually means a field failed validation.
- `401` means the workspace token is missing or invalid.
- `404` means the agent or skill name does not exist in the current workspace context.
- A skill can be listed even when the work is executed through another route. Use `contractReferences` to find the stable execution path.

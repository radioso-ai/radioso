# Data Model: Terminal Bootstrap Installer

## Overview

This feature adds a repository-root bootstrap workflow rather than a persisted product data model. The design centers on transient command-session objects and one filesystem-backed output file: `backend/.env`.

## Entities

### Bootstrap Session

**Purpose**: Represents one invocation of the default local start command from initial terminal render through final success or failure summary.

**Fields**:

- `startedAt`: timestamp when the command begins
- `mode`: whether the run is first-time setup, repeat start, or repair/update
- `ansiSupport`: detected terminal styling capability level
- `existingEnvState`: whether `backend/.env` is missing, partial, or valid
- `selectedOptions`: normalized setup choices that affect conditional prompts
- `result`: success, blocked, cancelled, or failed

**Relationships**:

- Contains many `Preflight Check Result` entries
- Contains one `Configuration Questionnaire`
- Produces zero or one `Startup Readiness Report`

**Validation Rules**:

- `mode` must be derived from actual repository state, not from user guesswork alone
- `result` cannot be success unless all blocking preflight checks passed and startup reached ready state

### Default Start Command

**Purpose**: Represents the repository-supported command surface developers use for both first-run setup and routine startup.

**Fields**:

- `invocationPath`: the repo-root command path exposed to developers
- `wrapperPath`: optional compatibility wrapper that forwards to the bootstrap module
- `entryModulePath`: actual Node module that owns the workflow
- `isPrimary`: whether this path is documented as the default start method

**Relationships**:

- Starts one `Bootstrap Session`

**Validation Rules**:

- Exactly one command path should be documented as primary for normal local startup
- Compatibility wrappers must not introduce divergent setup logic

### Preflight Check Result

**Purpose**: Captures the outcome of one prerequisite validation before configuration write or compose startup proceeds.

**Fields**:

- `name`: dependency or machine-state being checked
- `status`: pass, warning, or fail
- `summary`: one-line human-readable result
- `details`: optional diagnostic text
- `recoveryAction`: concrete next step for the developer
- `isBlocking`: whether the failure stops the flow

**Relationships**:

- Belongs to one `Bootstrap Session`

**Validation Rules**:

- Failing checks for Docker availability, compose availability, or required port conflicts must be blocking
- `recoveryAction` is required whenever `status` is fail

### Configuration Questionnaire

**Purpose**: Defines the ordered prompt flow for gathering only the values required by the chosen local setup path.

**Fields**:

- `questions`: ordered list of prompt definitions
- `responses`: normalized answers collected during the session
- `requiredKeys`: env keys that must be present before startup
- `generatedKeys`: env keys whose values are generated by the installer
- `skippedKeys`: env keys intentionally omitted because they do not apply to the chosen setup path

**Relationships**:

- Belongs to one `Bootstrap Session`
- Reads from one `Local Environment Contract`
- Produces one candidate `.env` payload for `Environment File State`

**Validation Rules**:

- Required keys must be fully resolved before write
- Secret responses must be masked from terminal echo and summary output
- Optional provider- or storage-specific questions may appear only when their enabling choice is selected

### Local Environment Contract

**Purpose**: Represents the canonical set of local configuration keys, stable defaults, conditional requirements, and generation rules used to produce `backend/.env`.

**Fields**:

- `keys`: ordered env key definitions
- `defaultValues`: stable default values safe to prefill
- `generatedValueRules`: secret or derived values the installer may create
- `conditionalRules`: conditions that determine when a key is required
- `validationRules`: value-shape and non-empty checks applied before write

**Relationships**:

- Drives one or more `Configuration Questionnaire` runs
- Materializes into one `Environment File State`

**Validation Rules**:

- The contract must stay aligned with `backend/.env.example`
- Generated defaults must never overwrite existing valid secrets without explicit user intent

### Environment File State

**Purpose**: Represents the repository-local `backend/.env` file before and after the bootstrap flow.

**Fields**:

- `path`: absolute file path
- `status`: missing, partial, valid, or invalid
- `existingValues`: parsed key/value pairs currently on disk
- `proposedValues`: merged values to be written
- `writeDisposition`: create, update, preserve, or no-op

**Relationships**:

- Read and written during one `Bootstrap Session`
- Produced from one `Local Environment Contract` and one `Configuration Questionnaire`

**Validation Rules**:

- Partial or invalid writes must not be persisted
- Existing valid values remain unchanged unless the user opts to replace them

### Startup Readiness Report

**Purpose**: Summarizes the outcome of compose startup and the final next steps shown to the developer.

**Fields**:

- `servicesChecked`: services whose readiness was evaluated
- `readyServices`: services that reached ready state
- `failedServices`: services that did not reach ready state
- `applicationUrls`: local URLs reported after success
- `nextSteps`: concise post-start guidance
- `logHint`: where to inspect deeper logs if startup failed

**Relationships**:

- Belongs to one `Bootstrap Session`

**Validation Rules**:

- Success output requires all required services to be ready
- Failure output must identify the blocking service whenever readiness is not achieved

### Terminal Presentation Theme

**Purpose**: Defines the visual treatment used to make the terminal flow branded and readable without making decoration a dependency for usability.

**Fields**:

- `palette`: color tokens for prompts, warnings, errors, progress, and success
- `headerArt`: the pixel-style sun-and-cloud composition
- `fallbackMode`: reduced visual treatment when ANSI or block rendering is unavailable
- `messageStyles`: formatting rules for headings, helper text, and recovery steps

**Relationships**:

- Used by one or more `Bootstrap Session` renders

**Validation Rules**:

- Prompts and recovery actions must remain understandable without color alone
- Decorative art may appear only at intentional points and must not interrupt input collection

## State Transitions

### Bootstrap Session

`starting` -> `preflight` -> `configuring` -> `writing-env` -> `starting-services` -> `ready`

Failure branches:

- `preflight` -> `blocked`
- `configuring` -> `cancelled`
- `writing-env` -> `failed`
- `starting-services` -> `failed`

### Environment File State

`missing` -> `create`
`partial` -> `update`
`invalid` -> `update`
`valid` -> `preserve` or `update`

### Startup Readiness Report

`pending` -> `ready`
`pending` -> `failed`

# API overview

The Radioso API has three access patterns.

- Session routes manage accounts, users, invitations, and workspaces.
- Workspace token routes handle documents, chat, search, settings, evals, and connectors.
- Public token routes handle anonymous chat and website embed flows.

In practice, that split matters more than the endpoint count. It tells you which credential to use and where state is stored.

## Start with the right path

- If you are signing users into the product, start with [Auth and sessions](/api/auth-and-sessions).
- If you are automating documents and chat from your backend, start with [Workspaces and tokens](/api/workspaces-and-tokens), then move to [Documents and search](/api/documents-and-search) and [Chat and history](/api/chat-and-history).
- If you are embedding anonymous chat on a website, start with [Public chat and embed](/api/public-chat-and-embed).
- If you are tuning workspace behavior, use [Settings](/api/settings).
- If you are evaluating answer quality, use [Evals](/api/evals).
- If you are managing external ingestion or messaging systems, use [Connectors and webhooks](/api/connectors-and-webhooks).

## Reference and scenarios

The key point is that there are two useful docs surfaces:

- [API Reference](/api-reference) for exact schemas, status codes, and payload contracts
- API scenario pages for the order in which you call those endpoints

The OpenAPI document at `backend/openapi.json` is the canonical reference source for both.

## System endpoint

Radioso also exposes a simple health route:

```text
GET /health
```

Use it for service monitoring and basic deployment checks.

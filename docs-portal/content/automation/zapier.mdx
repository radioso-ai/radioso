# Connect Radioso in Zapier

The Radioso app for Zapier works in both directions. A Zap can put a question to an agent, search the workspace's documents, add a document, and pull up a saved conversation. A Zap can also start when something happens in Radioso: a visitor leaves contact details, a routine finishes, a conversation is handed to a person.

The running example on this page is a support team. One Zap reads a new ticket, asks the Support agent about it, and writes the answer back into the ticket. Another adds a row to a sheet each time a visitor leaves a contact request.

## Connect your workspace

<Steps>

### Create a service account

Open **Settings → API access** in Radioso and create a service account with the `member` role. Copy the token from its first credential. It starts with `radioso_svc_v1_` and is shown once. See [Personal tokens and service accounts](/api/workspaces-and-tokens) for expiry and rotation.

### Add the Radioso app in Zapier

In a Zap, choose **Radioso** as a trigger or action app and select **Sign in**.

### Fill in the connection

| Field | What to enter |
|---|---|
| Instance URL | The URL your Radioso API answers on, over `https`: `https://api.radioso.ai` for the EU cloud, `https://api-us.radioso.ai` for the US cloud, or for a self-hosted deployment its app address plus `/backend`, such as `https://app.example.com/backend`. |
| Service-account token | The `radioso_svc_v1_…` token from the first step. |
| Workspace name | Optional. A name for this connection in Zapier's connection list. Without it, Zapier labels the connection with the instance host. |

A token only works on the instance that issued it, so pick the instance your workspace runs on. Zapier checks the connection with a call to `GET /api/v1/workspace/summary`. Zapier's cloud reaches public HTTPS addresses only, so a self-hosted Radioso needs one before the app can connect.

</Steps>

## Start a Zap from a Radioso event

Each trigger fires on one kind of [workspace event](/api/workspace-event-log). Pick the one that matches the moment you want to react to.

| Trigger | Fires when | What it carries |
|---|---|---|
| **New Conversation** | A conversation starts with an agent. | The conversation, agent, channel and visitor ids. |
| **New Contact Request** | A visitor leaves a contact request for the team. | `contactRequestId` and the collected `values`, such as a name and email. |
| **Handoff Requested** | A conversation goes to a person. | The handoff `reason`. |
| **Routine Completed** | A routine run ends. | `routineId`, the run's `executionId`, the `outcome` (`complete`, `handoff`, `action`, `stuck` or `consent_declined`) and the collected `values`. A sensitive value reads `[redacted]`. |
| **Decision Pending** | A routine waits for a person to decide. | `decisionHandle`, `routineId`, `stepId`, the author's `reason`, the `options` and the `deadline`. |

Every event also carries its `id` and `occurredAt`, and the conversation fields appear under `data`. An event holds ids and values, never a transcript. To read what was said, add a **Find Conversation** step with the event's conversation ID.

<Callout type="info">
**Decision Pending** only tells you that a decision is waiting. A person resolves it in the Radioso Inbox; a service-account token cannot.
</Callout>

### How a trigger works

Turning a Zap on registers a subscription in Radioso for that one event type, and turning it off removes it. Radioso signs every delivery, and the app checks the signature and rejects a delivery whose timestamp is more than an hour off before it starts the Zap. A subscription starts at the newest event, so a new Zap does not replay history. Zapier's test step shows the three most recent events of that type, so you can map fields before anything new happens.

Delivery is at-least-once and in order. If Zapier does not answer, Radioso retries the same event with a growing delay. The app remembers each event's `id` for two days and runs the Zap once per event, so a retry does not repeat it. If Zapier's cache is unavailable at that moment, the event is delivered rather than lost, so a rare repeat is possible; a Zap that must not repeat an action can also check the event `id` itself.

### One service account per Zap

A subscription belongs to the token that created it. Revoking that service account disables the subscription, and the Zap stops receiving events. Give each Zap its own service account so revoking one does not stop the others.

The token's role needs `workspace.event_subscriptions.manage`, `workspace.events.read`, and the read permission of each trigger: `workspace.history.read` for the conversation events, plus `workspace.conversation.takeover` for **Decision Pending**. The `member` role holds all of them.

Subscriptions are listed in Radioso under **Settings → API access**, with their state and last delivery, so you can see which Zap's subscription is failing or disabled. A subscription whose service account was revoked stays listed as disabled until you delete it there, and it counts toward the workspace's limit of 25 until you do. Turning a Zap back on, or republishing it, replaces the subscription for the same hook URL rather than adding a second one.

## Ask an agent

**Ask an Agent** sends a message to an agent and returns its answer. In the support Zap, map the ticket text to **Message** and choose the Support agent in **Agent**. Leave **Agent** empty to use the workspace's default agent.

The step returns:

- `conversation_id` and `assistant_message_id`, which identify the turn.
- `answer`, the agent's reply.
- `conversation_owner`, which is `human_owned` while a teammate has taken the conversation over and `ai_owned` otherwise.
- `reply_suppressed`, which is `true` when no agent reply was produced because a teammate owns the conversation. `answer` then holds the waiting message, so add a Filter on `reply_suppressed` before writing the answer anywhere a customer reads it.

To continue a conversation in a later step, map the earlier step's `conversation_id` into **Conversation ID**. It has to come from an earlier **Ask an Agent** step. The agent then sees the earlier turns, and the **Agent** field is ignored because a conversation belongs to the agent that started it.

The step calls the assistant chat API, `POST /api/v1/assistant/chat`, which is how a service account talks to an agent.

<Callout type="warning">
Zapier stops an action after about 30 seconds. An agent turn that runs a long routine or several skills can outlast that, and the step then fails with a timeout. A first turn that times out returns no conversation ID to look up, and Zapier's Autoreplay can send the same message again, so the agent may run the turn twice. Point Zaps at agents whose turns answer from documents.
</Callout>

## Search knowledge

**Search Knowledge** returns the passages in your documents that best match a query, without agent behavior: no persona, no history, no handoff. Choose an **Agent** to search only the documents that agent can use, or leave it empty to search the whole workspace.

The step returns `result_count`, the best match as `top_title` and `top_content`, and the full `results` list. A query with no match returns `result_count` `0` and does not fail the Zap. This is the retrieval search API, `POST /api/v1/retrieval/search`.

## Add a document

**Add a Document** sends a title and text to the workspace's knowledge. Radioso accepts a new document and processes it in the background, chunking it and computing embeddings, so the step returns a `document_id` and a `status` while the document is still being processed. Search finds it once processing finishes.

Set **External ID** to an identifier from your own system, such as a record ID. Sending the same External ID again replaces that document, and unchanged content returns `ready` at once.

## Find a conversation

**Find Conversation** looks up a saved conversation by its ID and returns its agent, channel, title, message count, owner, and a text transcript of up to 100 messages, each line labelled `customer`, `ai_agent` or `human_agent`. `transcript_is_partial` is `true` for a longer conversation. When no conversation has that ID, the search finds nothing, so a Zap can branch on it or carry on without it.

The transcript holds message text only. The visitor's profile and request details stay out of the Zap. Map the ID from an **Ask an Agent** step or from a trigger's `data` conversation ID.

## What the app does not cover

Replying as an operator, taking a conversation over, handing it back, and resolving a decision need a signed-in teammate's session. A service-account token cannot do them, so the app has no step for them.

## Common failure modes

- **Zapier says the connection is invalid.** The token is expired or revoked, or the instance URL names the wrong instance. A token issued by the EU cloud does not work on the US cloud. Create a new credential and reconnect.
- **A step returns `403`.** The service account's role lacks the permission the step needs. Use the `member` role or higher.
- **A trigger stops firing.** Check the subscription under **Settings → API access**. A subscription disabled because its service account was revoked needs a new service account and a reconnected Zap.
- **Turning a Zap on fails with a limit error.** A workspace holds up to 25 event subscriptions. Turn off or delete Zaps you no longer use.
- **Ask an Agent returns `404 agent_not_published`.** The agent has never been published. Publish it from the agent's page.
- **Ask an Agent times out.** The turn took longer than Zapier allows. See the note under [Ask an agent](#ask-an-agent).
- **A document is not found by Search Knowledge right after you add it.** Processing runs in the background. Check the document's status in **Sources**.

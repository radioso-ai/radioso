# Auth and sessions

These routes are the entry point for account creation, session establishment, invitation acceptance, email verification, and password reset.

## Relevant endpoints

```text
POST /api/v1/auth/register
POST /api/v1/auth/login
POST /api/v1/auth/email-verification/resend
POST /api/v1/auth/email-verification/verify
POST /api/v1/auth/password-reset/request
POST /api/v1/auth/password-reset/confirm
GET  /api/v1/auth/invitations/{invitationToken}
POST /api/v1/auth/invitations/{invitationToken}/accept
```

## How it works

<Steps>
### Register or inspect an invitation

Registration creates the account and default workspace bootstrap data. Invitation inspection lets a user confirm the target account before joining it.

### Verify or recover access if needed

Normal deployments can require email verification before login succeeds. Password reset uses the same shared mail pipeline.

### Establish the session

Login, invitation acceptance, and successful password reset confirmation return a session cookie.

### Use the session for account and workspace routes

Once the cookie is stored, use it for workspace management and token reveal flows.
</Steps>

The key point is that these routes establish browser or cookie-jar state. They are not the same as the workspace token flow used by the SDK.

## Register

Use registration when you want to create a new account and initial user in one step.

```bash
curl -sS \
  -H 'Content-Type: application/json' \
  -d '{"email":"you@example.com","password":"verysecurepassword","organizationName":"Acme"}' \
  http://localhost:8080/api/v1/auth/register
```

`organizationName` is optional. The required fields are `email` and `password`.

Registration returns account and default workspace bootstrap data. In the normal verified-email flow it does **not** automatically create a usable session cookie. Instead, the response includes `requiresEmailVerification: true`.

## Log in

Use login when the account already exists.

```bash
curl -sS -c cookies.txt \
  -H 'Content-Type: application/json' \
  -d '{"email":"you@example.com","password":"verysecurepassword"}' \
  http://localhost:8080/api/v1/auth/login
```

The login request can also include `preferredWorkspaceId` or `preferredAccountId` when you want to restore a known context.

## Email verification and password reset

Use `POST /api/v1/auth/email-verification/resend` to resend the verification email.

Use `POST /api/v1/auth/email-verification/verify` to consume the verification token.

Use `POST /api/v1/auth/password-reset/request` to request a reset link.

Use `POST /api/v1/auth/password-reset/confirm` to complete the reset. A successful reset confirmation also establishes a session cookie.

In local development, the default bootstrap flow writes `MAIL_DRIVER=log`, so verification and reset links are recorded in backend logs unless SMTP is configured.

## Invitation flow

In practice, the invitation flow has two steps:

1. Read the invitation details with `GET /api/v1/auth/invitations/{invitationToken}`.
2. Accept it with `POST /api/v1/auth/invitations/{invitationToken}/accept`.

The accept request establishes a session for the joined account.

<Callout type="info" emoji="i">
  Local development can bypass normal verification by setting `AUTH_SKIP_EMAIL_VERIFICATION=true`. That is a local shortcut, not the production contract.
</Callout>

## Common failure modes

- `400` usually means the request body is incomplete or malformed.
- `401` usually means the credentials are wrong, or the invitation accept flow is no longer valid.
- `404` means the invitation token does not exist.
- `409` usually means the account or invitation state is in conflict with the requested action.

# Document processing lifecycle

Document processing is the path that turns raw document input into searchable chunks. It is intentionally separate from live chat so uploads can be durable, retryable, and explicit about status.

## Lifecycle

<Steps>
### Ingest or import the document

Documents enter through either inline text ingestion or file import. Inline ingestion accepts title, content, optional metadata, and an optional external document id. File import accepts a multipart upload and preserves source file details.

A document's metadata is a flat map of key/value tags. Values are strings, numbers, booleans, or `null`, and the whole map is capped at 16 KB. Operators author it in the dashboard for inline and imported documents alike, and import accepts it up front. Replacing a document's metadata queues a fresh processing run, because tags reach the chunks at vectorize time.

### Queue background work

The API stores the document record and queues a processing job. The initial response is `202 Accepted`, not a completed indexing result.

### Materialize source content

For uploaded files, Radioso reads the stored source file and extracts normalized markdown or text content before chunking. Inline text documents skip this storage round-trip.

### Chunk the content

The worker loads workspace ingestion settings and applies the configured chunking strategy. Fixed-window, semantic, and recursive text chunking all map to workspace-scoped settings.

Fixed-window chunking always uses fixed-size overlapping text windows. Semantic and recursive text chunking first handle Markdown or HTML tables with repeated headers, then use code-aware chunking for fenced code blocks and source-code documents when parser support is available. Code-aware chunking is attempted for common shell, C-family, CSS, Go, Java, JavaScript, Kotlin, PHP, Python, Ruby, Rust, Scala, SQL, Swift, TOML, TypeScript, XML, and YAML inputs. If parser support is unavailable, processing falls back to text chunking.

### Embed and publish chunks

Each chunk carries an embedding and a metadata map of its own. That map is the document's metadata layered over the tags configured on its source — `{ ...sourceDocumentMetadata, ...documentOwnMetadata }` — so a key the document sets wins over the same key on the source. The document record keeps its own metadata only; source tags reach retrieval through the chunks.

Search text is rendered from a fixed slice of the merged map: the `dateFrom`–`dateTo` range, `sourceUrl` (falling back to `url`), and `author`. Every other key rides along on the chunk, available for metadata filtering, outside the embedded text.

The merge is computed on each vectorize pass, so a source whose tags change stamps them onto its already-indexed documents the next time those documents process. Reprocessing the source queues exactly that for every eligible document under it.

After chunking and before the chunk projection, the pass settles the tags extraction owns, using the same enablement the enrich job will run under. The projection always leaves extraction-owned keys out: they describe the previous revision's content, and the enrich patch rewrites chunk metadata but not the search text or vectors built here. When extraction runs on the new revision, the document itself keeps those keys and their provenance until the enrich run succeeds and replaces them, so a failed run leaves the document's extracted tags in place while its new chunks carry none of them. When extraction does not run, the extraction-owned keys and the provenance are cleared from the document too, because nothing will refresh them against the new content. Operator, connector, and source tags reach the chunks in every case.

Chunks are then published for the specific document revision so stale work does not overwrite newer content.

### Mark the document ready for retrieval

Once the worker publishes the chunks, the document becomes usable in document search and grounded chat. This happens without waiting for metadata extraction.

### Extract metadata asynchronously when enabled

Metadata extraction is optional and disabled by default. When enabled by the workspace setting, a source override, or a reprocess override, the worker queues a separate, lower-priority job after the document is already searchable.

That enrich job makes at most one model call for the document, plus the single retry described below. What the call looks for comes from the workspace document type catalog, which the job resolves through a read port at execution time rather than carrying on the job payload. Every job that runs after a catalog edit therefore sees the current catalog, and the run records the catalog revision it used. The queue message identifies the job by id, so the catalog reaches the worker through the database rather than the payload.

The catalog holds the built-in entries — `event`, `article`, `profile`, `reference`, and the reserved `generic` fallback — merged with the types an operator defines. Built-in definitions live in code and only their disabled flags are persisted. The rendered catalog section of the prompt is bounded at 12,000 characters on top of the 48,000-character document representation, enforced when the catalog is saved. A persisted catalog that renders past the budget is treated as an enrichment failure with a content-free reason. [Extract document metadata](/guides/document-metadata) covers authoring types and fields from the operator's side.

The call asks for structured output: a JSON Schema built from the enabled catalog, which lists its type keys and includes the `facts` payload only when a dated type is enabled and the `fields` payload only when an operator type declares fields. Providers that enforce a response schema enforce it; for the rest, the prompt carries the same shape and the reply is read as JSON, fenced or not. The first request runs at low reasoning effort with a 2,000-token output cap. A reply that cannot be used gets exactly one more request. A reply the provider reports as cut off at the cap is retried with a 4,000-token cap, which is what lets it finish on any provider, and at minimal reasoning effort, which only OpenAI's reasoning models honour. A reply that is empty, is not JSON, does not match the envelope, or matches a dated type with every fact dropped is asked again with the same request. On OpenAI that request is sampled again at the same low effort; on Claude, Gemini, and OpenAI-compatible endpoints it is the same request at temperature 0 and may well come back the same. The retry has its own usage attempt key, so both calls are metered, and the larger cap costs only the tokens the reply actually uses. Provider errors are not asked again at this level, because the adapters own transport retries: the OpenAI and OpenAI-compatible adapters go through the OpenAI SDK, which retries timeouts, 408, 409, 429, and 5xx responses twice with exponential backoff; the Claude and Gemini adapters call their APIs directly and do not retry. A second unusable reply, or any provider error, fails the run with a content-free reason: `invalid_output: truncated`, `invalid_output: not_json`, `invalid_output: empty`, `invalid_output: no_usable_facts`, `invalid_output:` followed by the envelope's failing field paths, or `provider_error`. When the run asked twice, the completion log and audit event also carry `firstAttemptFailureReason`.

A run asks the model only when the request is new. Each usable reply is stored on the document in `documents.enrichment_reply`, beside a fingerprint of the request that produced it: the system prompt with the rendered catalog, the document representation (title, created-at line, and body up to 48,000 characters), and the output schema. When a later run would send a request with the same fingerprint, it reads the stored reply instead, and everything after the call — validation, quote location against the new chunks, tag ownership, collisions — runs as it would on a fresh reply. A re-crawl of an unchanged page, a reprocess after a chunking or embedding change, and a metadata edit therefore cost no model call, while a title, body, prompt, or catalog change does. Document metadata stays out of the fingerprint because the model never sees it; the ownership rules read it on every run. The model name stays out too, so changing the deployment's chat model re-reads only documents whose request changes. A failed run keeps the last usable reply, and a stored reply that no longer reads as usable is asked for again. The stored reply quotes document text, so it is deleted with the document.

The model returns a classification envelope plus one payload: temporal facts for the built-in dated types, or an ordered array of `{ key, value }` pairs for an operator-defined type. Validation runs in two stages. The envelope resolves against the enabled catalog, and an unknown type key falls back to `generic` with no fields. Each field entry is then judged on its own: undeclared keys, values that fail their declared value type, duplicate keys after the first, and entries past the per-value and total size caps are each dropped and counted. No single drop fails the document.

Each temporal fact carries a `quote`: the text that states its date, copied from the document. The run locates the quote in the body after folding case, accents, whitespace runs, dash and quote styles, and Markdown emphasis markers, and records the matched span in body offsets — the offsets chunks use. A match must start and end on a word boundary: a letter or digit next to the quote's own first or last letter or digit rejects that occurrence, except in scripts written without spaces between words (Han, Hiragana, Katakana, Thai, Lao, Khmer, Myanmar) and in Hangul, whose particles attach to the date before them. Invisible format characters — soft hyphens, zero-width spaces, word joiners, byte-order marks — are folded out as well, and the span still points into the original text. A quote that repeats resolves in document order: to its first occurrence after the previous placed fact, else to its first occurrence. A quote found only in the title makes a document-wide fact with no span. A quote found in neither, an invalid calendar date, or an inverted range is dropped and counted in `droppedFactCount`, and so is a facts payload that is not a list, as one; a JSON-encoded list is read as the list. A fact with neither a date nor unresolved text is ignored and not counted. The remaining facts apply, unless the reply matches `event` or `article` and none remain: applying that would remove the previous run's dates and write none, so the reply counts as unusable.

Event dates are written to the document metadata as the overall span, and patched onto chunks as `dateFrom` and `dateTo`: each placed fact dates the chunks its span overlaps, a chunk overlapped by several facts carries their span from the earliest `dateFrom` to the latest `dateTo`, and a document-wide range dates every other chunk. The range is document-wide when every fact names it, or else when every fact quoted from the title names it, and only when the run dropped no fact and every event fact resolved to a date; otherwise the chunks no fact covers stay undated. Article publication dates attach at document level. Operator-defined fields are document-level scalars copied to every chunk in the same patch, so a metadata rule on one of them matches the whole document. A document that already carries dates of its own, or whose source stamps dates on its chunks, keeps those on every chunk instead, as [Who owns an extracted tag](#who-owns-an-extracted-tag) describes.

The completion log and the `document.enrichment` audit event carry the run's status, its coded `outcome`, its `factCount`, `droppedFactCount`, `appliedChunkCount`, `skippedCollisionCount`, and `modelAttemptCount`, and the failure reason; the enrichment trace span carries the status, the outcome, and the same fact, dropped-fact, applied-chunk, and model-attempt counts, from the same source. `modelAttemptCount` counts model requests within one run, apart from the job's own `attemptCount`, and is 0 when the run reused a stored reply. None of them carries document text, quotes, or model output.

The outcome is one of `applied`, `applied_after_truncation` (the first reply hit the output cap and the retry's reply applied), `reused` (a stored reply applied with no model call), `truncated` (the retry's reply hit the cap too, and nothing was stored), `invalid_output`, `provider_error`, or `catalog_over_budget`. Each run also emits a `document.worker.enrichment_completed` telemetry event tagged with it, which the metrics sink counts as `radioso_document_worker_events_total{event_type="document.worker.enrichment_completed",outcome="..."}`. The two cap outcomes are the ones to watch: each is a reply long enough to cost a second request or lose the run. Every model call the run makes is recorded in the usage ledger under `documents` / `document_enrichment`, attributed to the workspace's account and linked to the document and the revision it read, with input, output, reasoning, and cached-input tokens.

Patching chunk metadata recomputes the stored `date_from` and `date_to` columns that temporal retrieval reads. The patch merges over the metadata a chunk already carries, so source and document tags stay in place beside the extracted values, and a key extraction gives up falls back to the value the source stamps under it. No re-embedding is needed, because those columns are structured and not part of the vector.

</Steps>

## Who owns an extracted tag

Extraction owns exactly the keys it generated for a document. Provenance in `documents.enrichment` records that set alongside the matched type key, the catalog revision, and content-free counts of applied, dropped, and collision-skipped fields. That recorded set — not a hard-coded key list — drives stale-tag cleanup, so a field removed from a type stops leaving orphaned tags behind.

A key already set on the document that is not in the generated set is manually authored or connector-supplied, and a key the source's document tags set is the source's. Extraction skips either one and counts the collision; a `null` or blank value counts as unset, so extraction may fill it in. A manual metadata write that changes or removes a generated key drops that key from the set in the same statement, handing ownership to the operator for good.

Tag replacement is atomic with success: only after validation succeeds does a run remove the previous generated keys, write the new ones, and replace provenance in a single persisted update. A run that fails records its failure fields and leaves existing tags, the prior generated-key set, and the last successful run's catalog revision intact. The document stays searchable throughout; a failed enrich job never changes its ready status.

The built-in `dateFrom` and `dateTo` keys follow the same rule, as a pair. A run that writes them records both in the generated-key set. When the document already carries either one — written by an operator or an API client — or its source's document tags carry one, the run writes no date to the document or to any chunk, counts each date it would have written as a collision, and the chunks keep those dates from the projection. A `null` or empty value counts as no date. A manual write that changes or removes either extracted date hands both to the operator.

Dates on a document a connector syncs are the connector's defaults: WordPress, for one, writes each post's publish day as `dateFrom`. A run that reads dates replaces them on the document and on every chunk, and the dates it writes become extraction's; a run that fails or reads no dates leaves them standing. The connector rewrites a synced document's metadata on its next sync anyway, so a hand edit to those dates lasts until that sync or until a run reads dates.

The document API publishes the keys extraction owns as `generatedKeys`, dates included.

## Why revisions matter

Document processing is revision-aware. If a document is updated while an older job is still running, the older job is treated as stale and does not publish outdated chunks over the newer revision.

## Source kinds

- Inline text documents store their source content directly in the document record.
- Uploaded files store source file details and are materialized during processing before chunking begins.
- Website and connector sources can carry a source-level metadata extraction override. That override can inherit the workspace default, force extraction on, or force it off.
- A source record also holds `documentMetadata`: the document tags stamped onto the chunks of every document under that source. It takes the same shape as a document's own metadata — flat key/value pairs, scalar values, 16 KB for the map — and the same key on a document overrides it.
- Manually added documents have no source record, so their override is a workspace ingestion setting that offers the same three choices and fills the same slot when processing resolves whether to extract. With no source record there are no source tags either, so each of those documents carries the metadata it is given.

## Queue payloads

Document processing jobs are durable PostgreSQL rows. Queue dispatch, including AMQP and Cloud Tasks, sends only the job identity needed to wake a worker. The worker reads the row to learn what to do, so the queue message shape does not change.

Each job row carries a `kind`: `vectorize` for the indexing pass that makes a document searchable, and `enrich` for the follow-up metadata extraction. The worker claims `vectorize` jobs before `enrich` jobs, so a large import indexes everything first and extraction drains afterward at lower priority.

Reprocess options such as `documentEnrichmentOverride` live on the processing job row and are copied onto the enrich job. Retries and reschedules preserve the same row options.

## Failure and verification

If a newly uploaded document does not influence answers yet, verify these in order:

1. the document exists in the workspace
2. its status moved out of pending or processing
3. processing did not record a failure reason
4. the document actually produced chunks for the latest revision

<Callout type="warning" emoji="!">
  A missing answer for a newly uploaded document is often a processing-status problem, not a retrieval-ranking problem.
</Callout>

# Data Residency

Radioso's own backend, database, and documents run wherever you deploy them. A handful of outside services sit behind that: a model provider for chat and embeddings, a voice vendor for calls, an email provider for outbound and inbound mail, product analytics, Slack, and Stripe. Each one decides where it processes the data you send it, and that's a separate question from where Radioso itself runs. This page lists each one, what it handles, and the setting — if there is one — that controls its region.

## OpenAI

The native `openai` provider backs chat, embeddings, and rerank. By default, platform-held OpenAI traffic goes to OpenAI's global API. Set `OPENAI_DATA_RESIDENCY=eu` or `OPENAI_DATA_RESIDENCY=us` on the backend, document worker, and crawler worker to send it to OpenAI's EU or US data-residency endpoint instead.

Getting OpenAI itself to process requests in-region takes its own setup, separate from this flag:

1. Apply for OpenAI's abuse-monitoring controls and sign its Modified Retention amendment. Regional processing requires both.
2. Create a project with its region set to Europe (or United States) and issue an API key from it. An existing project can't change region later. A key from a project with Global geography reaches chat and Responses on the regional endpoints once your organization is eligible. The regional embeddings endpoint accepts only keys from a project created with a region.
3. Confirm every model you use, including the embedding model, supports regional processing in that region.
4. Set `OPENAI_DATA_RESIDENCY` and `OPENAI_API_KEY` (the regional project's key) together, then redeploy. Each runtime — the backend, the document worker, and the crawler worker — checks the key against its regional embeddings endpoint once at startup, before it serves traffic, and refuses to start if that endpoint rejects it. An OpenAI outage during that check only logs a warning and lets startup continue, so a transient OpenAI problem never blocks an otherwise-good deploy.

A workspace's own OpenAI key (Settings → Providers, bring-your-own-key) always uses OpenAI's global endpoint, regardless of `OPENAI_DATA_RESIDENCY`. A workspace key's requests are therefore processed globally. A key from a project created with a region (a Europe-region project, for example) isn't supported as a workspace key, because that project is only reachable on its own regional host.

## Anthropic and Gemini

Claude and Gemini each take either a platform-held key (`ANTHROPIC_API_KEY`, `GEMINI_API_KEY`) or a workspace's own key. Both call their provider's global endpoint either way; there's no region setting for either provider.

## ElevenLabs (voice channel)

A voice runtime key is a workspace's own ElevenLabs account, set under Settings → Providers → Voice runtime keys. The agent's **Voice** card picks that account's **Data residency** — United States (the default), European Union, India, or Singapore — and it has to match whichever region the ElevenLabs account itself is provisioned for. EU residency needs an Enterprise ElevenLabs account; picking it on an account that isn't Enterprise reads like a wrong key, because the account's data only ever lives on its region's host.

## Resend (email)

Resend sends and receives mail for the email channel. `RESEND_CHANNEL_REGION` picks the region of the sending domain Resend provisions for the channel — `eu-west-1` for an EU deployment, `us-east-1` by default. It doesn't move Resend's own account data, delivery metadata, logs, or received message content, which Resend keeps in the United States regardless. If your deployment needs a safeguard for that transfer — standard contractual clauses, for example — put it in place separately; this setting doesn't provide one.

## PostHog and OTEL log export

PostHog product analytics and PostHog error reporting (`PRODUCT_ANALYTICS_SINKS` or `ERROR_SINKS` including `posthog`, an Enterprise Edition sink) send to `POSTHOG_HOST`. Point it at PostHog's EU ingestion host (`https://eu.i.posthog.com`) to keep that data in the EU, or its US host to keep it in the US.

OTEL log export is a separate mechanism with its own setting, `OTEL_EXPORTER_OTLP_LOGS_ENDPOINT`; it doesn't read `POSTHOG_HOST`. As a Terraform convenience, the Terraform module defaults `OTEL_EXPORTER_OTLP_LOGS_ENDPOINT` to `<posthog_host>/i/v1/logs` when OTEL logs are enabled and no explicit endpoint is set, but a deployment that sets `OTEL_EXPORTER_OTLP_LOGS_ENDPOINT` directly controls its own region independently of `POSTHOG_HOST`.

## Slack and Stripe

The Slack and Stripe integrations each reach their provider's global, US-based API. Neither has a region setting.

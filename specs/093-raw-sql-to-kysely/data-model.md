# Phase 1 Data Model: Raw SQL → Kysely

**Feature**: 093-raw-sql-to-kysely
**Date**: 2026-06-21

This migration introduces **no new database tables and no schema changes**. The
PostgreSQL schema (system of record: `backend/src/db/migrations/*.sql`) is unchanged.
What changes is the *type layer* the backend uses to talk to that schema. This document
defines the new type seams and the invariants the migration must hold.

## New type seams (code, not database)

### 1. Generated database schema — `Kysely` `DB` interface

- **Location**: `backend/src/shared/infra/kysely/schema.ts` (generated; do not edit).
- **Shape**: one TypeScript interface per table, where each property is a column typed
  for select/insert/update (Kysely `ColumnType`/`Generated`/`Selectable`/`Insertable`).
  A top-level `DB` interface maps table name → row interface.
- **Source**: produced by `kysely-codegen` introspecting a database that has had all
  `migrations/*.sql` applied. Regenerated by `pnpm --dir backend run db:types`.
- **Custom column type mappings** (codegen overrides):
  - `vector`, `vector(1536)` → `string` (serialized `[a,b,c]` literal, matching current
    `serializeVector`).
  - `tsvector` → `string`.
  - `jsonb` → `unknown` (or a narrowed type via per-column override) — repositories keep
    parsing/validating JSONB in their row mappers, not in the DB type.
  - `bigint`/`numeric` columns that the driver returns as `string` keep their existing
    coercion in row mappers (e.g. byte counts, token sums).

### 2. Injected executor type — `Db`

```text
type Db = Kysely<DB> | Transaction<DB>
```

- Repositories receive a `Db` (replacing today's injected `Database`). Both `Kysely<DB>`
  and `Transaction<DB>` expose the same query-builder API, so a repository method works
  identically whether called standalone or inside a transaction.
- The connection-pool-owning `Database` (or a thin successor) still exists for pool
  lifecycle, the migration runner's raw path, and constructing the `Kysely<DB>` instance.

### 3. Typed SQL-fragment helpers

- **Location**: `backend/src/shared/infra/kysely/sqlHelpers.ts` (name TBD).
- Owns every Postgres-specific expression as a typed `sql` fragment, e.g. (illustrative
  names): `vectorDistance(column, queryParam)`, `castVector(value, dims?)`,
  `vectorDims(column)`, `tsMatch(column, query)`, `tsRankCd(...)`, `jsonbContains(...)`,
  `jsonbPathText(...)`, `anyOf(values, pgType)`, `forUpdateSkipLocked(...)`,
  `setLocal(name, value)`.
- This is the single allowed home for raw SQL fragments in application code (besides the
  migration runner). The FR-014 guard allowlists exactly this file and the runner.

## Unchanged boundary types (must NOT drift)

- **`*Row` interfaces** (snake_case): keep describing DB columns. With Kysely these can
  often be derived from `Selectable<DB['table']>`, but the row→record mapping stays.
- **`*Record` types** (camelCase): the domain-facing boundary returned by repositories.
  **Invariant**: `*Record` must not import or reference `DB`, `Kysely`, or any Kysely
  type. Domain modules remain ignorant of the persistence library.
- **`*RepositoryPort` interfaces**: unchanged. Domain modules depend only on these.
- **`*RowMapper` modules**: unchanged in responsibility; still convert rows → records and
  still own numeric/Date/JSONB coercion.

## Invariants checklist (per migrated repository)

For each repository, the migration is correct only if all hold:

1. Public `*RepositoryPort` signature is byte-for-byte unchanged.
2. Returned `*Record` objects are field-, type-, and order-equivalent to the raw-SQL
   output for the same inputs.
3. Upsert conflict targets/actions, `RETURNING` columns, and row-lock clauses are
   preserved.
4. Pagination boundaries and ordering are identical.
5. Numeric/Date/JSONB coercion in the mapper is unchanged.
6. The repository's tests (existing + any new characterization tests) pass.
7. No raw SQL string remains in the repository (only Kysely + allowlisted helpers).

## Entity relationship

No ERD change. The relational model, foreign keys, indexes (including `pgvector`
ivfflat/hnsw indexes and FTS GIN indexes), and constraints are exactly as defined by the
existing migrations. Kysely queries must continue to hit the same indexes (verify via
`EXPLAIN` on the retrieval and pagination hot paths).

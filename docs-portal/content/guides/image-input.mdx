# Let visitors send photos

Some requests are easier to show than to write. A client looking for a property sends a photo of the kind of place they have in mind, a customer sends the product they want to replace, someone sends the letter they are holding. Turn on photos for an agent and the visitor attaches up to three photos to a message. The agent's chat model reads each photo once, and what it reads becomes part of what the visitor said, so routing, routine slots, retrieval and skills all work from it with no extra setup.

## Turn photos on

Open the agent's **Profile**, find **Answers**, turn on **Let visitors send photos**, and choose **Save draft**. The switch is part of the agent's draft, like its instructions: Test Chat tries it once the draft is saved, and visitors get it when you publish the agent with **Review & publish**. Until then the revision header reads **Draft changes**. Photos reach visitors only from a published version that turns them on, so an agent that has never been published takes none. You can also ask Ray to turn it on and apply the card it drafts, or set `visitorImagesEnabled` on the draft over the API, then publish:

```bash
curl -sS -X PUT https://api.radioso.ai/api/v1/agents/$AGENT_ID \
  -H "Authorization: Bearer $RADIOSO_API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"visitorImagesEnabled":true}'
```

Photos take effect only when the agent's chat model reads images. Every model in Radioso's catalogue does; an `openai-compatible` endpoint is treated as one that does not, because Radioso cannot know what model it serves. The agent settings say whether that holds. `chatModelReadsImages` is a read-only boolean on `GET /api/v1/agents/{agentId}` and on the answer to `PUT /api/v1/agents/{agentId}`, computed from the model the agent answers with, which Radioso decides from the agent's own model, the workspace's chat model and the plan, as it does for a turn. It is `true` or `false` whatever `visitorImagesEnabled` says. When it is `false`, the dashboard says so beside the switch: the switch stays off until you pick another model, and a setting that was already on reads "Not working" until you do.

The public chat says whether the agent takes photos right now in `acceptsImages`: on the session response, and on the conversation list a chat reads when it loads or reloads (`GET /api/v1/public/chat/{token}`). It is `true` only when the agent's published revision has photos on and `chatModelReadsImages` is `true`, and a client shows an attach control only then. Every live channel decides the same way: the website widget, the public link, the REST agent channel, `POST /api/v1/assistant/chat` and its image upload, and WhatsApp. A chat that reloads reads it afresh, so a change you publish shows up in the next page load.

## What visitors see

On an agent that takes photos, the composer in the website widget and on the public chat link shows an attach button beside the message field. A visitor picks up to three photos from the file picker (JPEG, PNG or WebP; on a phone the picker offers the camera too), or pastes or drops them on the composer.

Each photo appears as a small preview with a spinner while it uploads and the agent reads it, which takes a few seconds. Photos are shrunk one at a time, so a phone does not hold several full-size photos in memory at once, and the preview shows the photo as it was shrunk. A cross on the preview removes it, from the keyboard too: each cross is named for its photo ("Remove photo 2 of 3"), and focus moves to the next photo's cross, then to the attach button, then to the message field. Error lines are red where red reads at 4.5:1 on the chat's colours, and black or white where it does not. A photo that fails shows a warning on its preview and a line saying why: the type is not accepted, the photo is too large, photos cannot be sent right now (the agent stopped taking them, or the plan has no answers left), or it could not be uploaded. A server too busy to take a photo is tried once more after a moment; if it is still busy, the preview says so, and the visitor can remove the photo and attach it again. Dropping a fourth photo says that a message carries three.

When the operator turns photos off after a visitor attached one, the send is refused: the photos leave the composer with a line saying photos cannot be sent right now, the thread shows nothing was sent, and what the visitor typed is back in the message field to send on its own. The chat then stops offering photos, and the line stays on screen after the attach button has gone. A photo that was uploaded before photos went off is dropped too, and never counts as something to send.

A send that fails before the server takes the photos, because the network dropped or a rate limit held it back, gives the photos and the words back in the composer, uploaded as they were, so the visitor sends again without attaching again. Each photo's reading already counted as a plan answer, so it is not thrown away. A file dropped anywhere else on the chat, outside the composer, does nothing, so the browser does not navigate away from the conversation to open it.

Send is ready as soon as there is text or an uploaded photo, so a photo alone is a message, and it waits while any photo is still uploading. The browser shrinks each photo before it goes up, to a JPEG of at most 1,600 pixels on the long side, so a several-megabyte phone photo travels as a few hundred KB. In the thread, the visitor's bubble holds their photos and what they typed, and a reload shows the same.

The attach labels and the messages for a photo that cannot be sent come with the widget's built-in translations in every language it speaks.

## What a teammate sees

In Activity, a message with photos shows a thumbnail for each photo above the text the visitor typed, in the conversation view and in the drawer. A photo is asked for once it scrolls into view, and each photo the browser loads is recorded as a `conversation.image_viewed` audit event, so the record means the photo was on screen: one far down a long conversation is not recorded until you scroll to it. Under the visitor's bubble, **What the agent read** opens the agent's reading of each photo, kept apart from the visitor's own words. Seeing photos takes the `workspace.history.read` permission.

## Try photos in Test Chat

Test Chat takes photos the way the web chat does, so you can see what a draft makes of a reference photo before a visitor sends one. When the version you test takes photos, the Test Chat composer shows the same attach button: pick up to three photos, or paste or drop them on the composer, and each one is shrunk in your browser, uploaded and read while you type, in your browser's language, as a visitor's photo is read in the visitor's. Send the message with or without text. Every version you test answers from the same readings, so a comparison shows how two versions handle one photo.

Your message shows your photos and what you typed. **What the agent read** under it opens the reading of each photo, which is what the version under test actually ran on; it says the reading is loading until the test has saved the message. A message that never reaches the test, because the network dropped or another turn is still running, comes back to the composer with what you typed and its photos. Reopening the test from **Conversation history** shows the same. A photo sent in a test stays with that test and is deleted with it, under Test Chat's own retention. A test you continue from a real conversation with **Continue in test chat** shows the visitor's photos too. Every teammate can open a test, so each photo that loads in Test Chat is recorded in the audit log: a visitor's as a `conversation.image_viewed` event, as it is in Activity, and any other as an `agent.test_execution.image_viewed` event naming the test.

Whether Test Chat takes photos follows the version under test. Test Chat tests the saved draft, so turning photos on and saving the draft lets you try them there before you publish; visitors keep what the published version says. A version you pick from the history uses its own switch, and a comparison takes photos only when both versions do. The chat model belongs to the agent, so when photos are on but the model cannot read images, Test Chat says so under the composer.

Each photo read in Test Chat counts against the plan as a test run, as a test message does. Talk sends what you say, so attach photos to a typed message. Ray reads each photo's reading in a test's transcript and sends text: `send_test_chat_message` attaches no photos.

Over the API, with a token that can manage the agent, upload each photo for the test with `POST /api/v1/agents/{agentId}/test-executions/{executionId}/images`, which takes it when the versions the test runs have photos on, and send the returned ids as `imageIds` to `POST /api/v1/agents/{agentId}/test-executions/{executionId}/messages`, with or without `message`. A photo is sent by the credential or signed-in user that uploaded it, once, and its reading counts as a test run, as a test message does. Sending a message again with the same `turnId`, `attemptId` and `imageIds` after it completed replays its answer, and the photos stay with the turn that first took them. In the test's history, a user entry with photos carries `imageInput`, and a teammate opens a photo with `GET /api/v1/agents/{agentId}/test-executions/{executionId}/images/{imageId}` in a dashboard session.

## What the agent reads

A message carries up to three photos, with or without text. Each photo is read as soon as it is uploaded, while the visitor is still typing, so sending is no slower than a plain message.

The reading is a short factual description written for search and matching: what the thing is, its style and era, the setting, materials and colours, notable features and condition, and any text visible in the photo, quoted. It is written in the visitor's language, or the agent's default language when the visitor's is unknown. It never names or describes a person, and it says when it is unsure.

The agent's turn runs on the visitor's text followed by one block per photo:

```text
Something like this, near the coast
<attached_photo index="1">A two-storey stone farmhouse with a terracotta tile roof and green wooden shutters, set among olive trees. Possibly 19th century.</attached_photo>
```

When the model cannot read a photo, its block is `<attached_photo index="1" status="unreadable"/>`: the turn text still says a photo came with the message and that it could not be read, and the message goes through. Text visible in a photo reaches the agent only as the reading quotes it, and the reading prompt asks the model to quote such text as content rather than follow it. A reading keeps its text as written, with `<` and `>` escaped so it stays inside its block.

The stored message keeps both forms. Its `content` is the turn text above, which summaries, exports and Ray's transcripts read. Its `inputMetadata.imageInput` holds what the visitor typed (`typedText`) and each photo's `id` with its `reading`, so a thread shows the visitor's own words and the photos, with the readings kept apart as the agent's. A teammate opens a photo from the conversation with `GET /api/v1/conversations/{conversationId}/images/{imageId}` in a dashboard session; each view is recorded as a `conversation.image_viewed` audit event.

## Limits

- **Formats.** JPEG, PNG or WebP, read from the file's bytes rather than its name.
- **Size.** At most 10 MiB per upload, and three photos per message. Each photo is sent once.
- **What is stored.** A JPEG at most 1,600 pixels on its long side and at most 512 KB, turned upright, with its EXIF and GPS data dropped. A client that shrinks photos before uploading, to about the same size, saves the visitor most of the upload.
- **How long.** A photo sent with a message stays with its conversation and is deleted with it, by hand or by the workspace's retention window. A photo attached and never sent is deleted 24 hours after its upload. See [Data retention](/operators/data-retention).
- **Rate.** Uploads have their own budgets: 20 per ten minutes for one visitor session and network source, 40 for the source, 600 for the workspace; 120 per ten minutes for one API credential.
- **Plan.** Each photo the agent reads counts as one answer against the workspace's plan, on its own rather than inside a conversation's block of replies. A photo the model could not read costs nothing. Once the plan is used up, an upload is refused with `429 usage_limit_exceeded`, the same refusal a message gets.

## Match a photo against your catalogue

The reading is text, so the tools you already use take it from there. For the property-matching case, author a **brief** routine with text slots the photo can fill — property type, style, era, notable features — next to the slots only the visitor can answer, such as region, dates, budget and contact details. The routine fills the first group from the reading and asks for the rest.

Then run one of two lookups:

- **A `retrieve` step** over a corpus with one document per property. Answers come with citations to the properties they matched.
- **An `external_mcp` skill** whose exposed parameters bind to the slots, for a live property database.

Two things to keep in mind on the second path: a routine skill's result reads best as text rather than a nested object, and a directive-bound MCP skill needs the tool to return a text answer. See [Author a routine](/guides/authoring-routines).

## Send photos over the API

Upload each photo for the agent, then send the returned ids with the message. With a personal or service-account credential:

```bash
curl -sS -X POST "https://api.radioso.ai/api/v1/assistant/images?agentId=$AGENT_ID" \
  -H "Authorization: Bearer $RADIOSO_API_TOKEN" \
  -F "image=@farmhouse.jpg" -F "locale=it"
# {"id":"6c3e9f2a-1d4b-4b8e-9f0a-2a4c6e8b0d12","readingStatus":"read"}

curl -sS -X POST https://api.radioso.ai/api/v1/assistant/chat \
  -H "Authorization: Bearer $RADIOSO_API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"agentId":"'$AGENT_ID'","message":"Something like this, near the coast","imageIds":["6c3e9f2a-1d4b-4b8e-9f0a-2a4c6e8b0d12"]}'
```

The upload answers once the agent has read the photo: `readingStatus` is `read`, or `unread` when the model could not describe it. `locale` sets the language of the reading. A message may carry `imageIds` alone. The photo belongs to the credential that uploaded it, so only that credential can send it, to the same agent.

With the [TypeScript SDK](/sdk/basic-usage#send-photos):

```ts
const photo = await client.chat.uploadImage({
  agentId,
  image: await fs.readFile('farmhouse.jpg'),
  mimeType: 'image/jpeg',
  locale: 'it',
})

const response = await client.chat.create({
  agentId,
  message: 'Something like this, near the coast',
  imageIds: [photo.id],
})
```

A client holding a REST credential bound to one agent uses `POST /api/v1/agents/{agentId}/images` and sends `imageIds` to `POST /api/v1/agents/{agentId}/chat` the same way.

A page of your own on the public chat uploads to `POST /api/v1/public/chat/{token}/images` with the visitor's public session in `x-radioso-public-session`, sends `imageIds` with the message, and reads a photo back with `GET /api/v1/public/chat/{token}/images/{imageId}`, which serves only the session that uploaded it. See [Public chat and embed](/api/public-chat-and-embed#send-photos).

## Photos on WhatsApp

A photo sent to a connected WhatsApp number is read the same way, with nothing to upload: Radioso downloads it from WhatsApp with the connector's access token, and it goes through the same checks, re-encoding, reading and storage as a photo from the web chat. The caption is the message text, and the photo is the image. A photo with no caption is a message made of the photo alone.

WhatsApp delivers an album as separate messages a few seconds apart. Radioso answers messages from one number that arrive within three seconds of each other as one turn, so up to three photos sent together, with the caption on any of them, are one message to the agent and get one reply. A fourth and later photo in the same turn is handled as an unsupported message, and a photo sent after the turn has been answered starts a turn of its own.

The agent that answers is the one the number's conversation already runs on, or the workspace's default agent when a new conversation starts. When that agent has photos off or its chat model cannot read images, a photo is an unsupported message, exactly as it is without this setting: Radioso sends the connector's unsupported-message reply if you configured one, and records the message as skipped otherwise. See [Connectors and webhooks](/api/connectors-and-webhooks#built-in-connectors).

A WhatsApp photo counts against the plan like any other photo. When the plan is used up, or Radioso is busy processing other photos, the photo is handled as a text message would be in the same situation: Radioso retries it a few times, and a message that still cannot be answered is recorded as failed. A retry reuses the photos an earlier attempt already stored and read, so it does not download them again or count them against the plan twice. If you turn photos off for the agent while a photo is on its way, the photo becomes an unsupported message, and the caption and any text sent with it are answered on their own.

A WhatsApp photo is bounded like any other upload: 10 MiB at most, read by its bytes, and stored as a re-encoded JPEG with the conversation. A photo WhatsApp no longer holds, one over the cap, one that is not an image Radioso can read, or one whose download WhatsApp refuses (for example because the connector's access token is rejected) is not read: its caption is answered as text, and a photo with no caption is an unsupported message, with the unsupported-message reply when you configured one. A download that fails for a reason worth another try is retried first.

## Common failure modes

- **No attach button in the chat** — the published version has photos off (turning them on in the draft reaches visitors once you publish), the chat model cannot read images, or the chat loaded before you published. Reload the page: the website widget and the public link read the setting each time they load, and a widget that is only closed and reopened keeps what it had.
- **No attach button in Test Chat** — the draft has photos off (save it after turning them on), or the chat model cannot read images, which Test Chat says under the composer. Test Chat reads the setting when you open it, so switch tabs back to it after changing the setting. A photo for a version that has photos off is refused with `404 visitor_images_unavailable`.
- **A WhatsApp photo gets the unsupported-message reply, or no reply** — the agent that answers the number has photos off, or its chat model cannot read images. Turn photos on for that agent, or give it a model that reads images.
- **`404 visitor_images_unavailable` on upload** — the published version has photos off, or the chat model cannot read images. `acceptsImages` is `false` in both cases. On a Test Chat upload, the version under test has photos off.
- **`415 unsupported_image_type`** — the file is not a JPEG, PNG or WebP image, whatever its name says.
- **`413 image_too_large` or `image_too_many_pixels`** — over 10 MiB, or too many pixels to decode. Send a smaller photo.
- **`503 visitor_image_busy` on upload** — the server is decoding as many photos as it takes at once and none finished within a few seconds. Try the upload again.
- **`429 usage_limit_exceeded` on upload** — the workspace's plan has no answers left for the reading. The public chat routes leave out the plan `details`; the API routes carry them.
- **`400` on `POST /api/v1/assistant/images`** — `agentId` is missing from the query or is not an agent id.
- **`409 visitor_image_unavailable` on send** — the id is unknown, was uploaded by another session or credential or for another agent, or a message already carried it: upload the photo again. It is also the answer when the agent stopped taking photos after the upload, because a version with photos off was published or its chat model changed to one that cannot read images; then the message goes without them.
- **`readingStatus: "unread"`** — the model did not answer in time or could not describe the photo. The message still carries the photo, and its block in the turn text reads `status="unreadable"`.

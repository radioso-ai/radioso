# Author a routine

A directive steers one turn. A routine carries a flow across many turns: it can
collect values, call a skill, take a branch, and finish or hand off to a person.
Use a routine for an order-issue intake, lead capture, or refund check.

In an agent's **Routines** settings, choose **New routine** to start one, or
select an existing routine to open the editor.

## The routine document

The editor presents the routine as a document: the flow as readable instructions,
with typed controls at each decision. The engine compiles it into the graph it
runs, so you work with the routine instead of drawing the graph.

Every change saves into the agent's private draft as you make it, so the document
is always the form a colleague reads to learn what the agent does.

![The Damaged delivery intake routine open in the routine editor, with the routine's name as the page title, a Draft pill beside it, the collapsible When to trigger section holding the Activation trigger, two required text slots named order_number and issue_description, and the first numbered step.](/screenshots/dashboard-routine-editor.png)

### Work in the document

Document opens with a collapsible **When to trigger** section holding
**Starts when**, followed by **Instructions** — the numbered steps and their
branch rows. **Information**, **Endings**, and **Completion export** sit
inside an **Endings & information** disclosure at the bottom, closed by
default. A skill step shows its **uses → sets** bindings in its step editor,
opened from the step's own token, so the flow also shows where information
comes from and goes without crowding the sentence.

Edit the starts-when line directly. In a step instruction, type `@` to capture a
value, then choose its type in **Information**. Use **+ Step** to add chat,
skill, approval, or action steps. Condition rows choose a **Rule** or **AI
decides** decision and its target. Ending rows set the message for a completed or
handed-off flow. Delete a step with Backspace in its empty instruction, the
trash next to its reorder arrows on hover, or the step editor panel; a branch
that pointed at it retargets to a new, blank ending.

Validation notes appear beside the row or field that needs attention. They point
to issues such as a missing target, an unset required skill input, or a comparison
whose value type needs adjustment.

## Set the routine header

The routine's name is the page title — click it and type a new one. A pill
beside it reads **Draft** or **Live**, and the round button next to the pill
switches between them. On a blank routine, **Draft from procedure** is a visible
starting option; it is also in the overflow menu with **Delete routine**.
**Test** opens the draft in Test Chat.

Open **When to trigger**, then **Starts when**, to set:

- **Priority** — higher whole numbers win when several routines could start at
  once. Use 0 for the standard priority.
- **Reentry** — what happens after the routine finishes in a conversation.
- **Activation trigger** — a plain-language description of when the routine
  should start.

The trigger is judged by meaning, so write it the way an operator would describe
the task: “customer reports coffee that arrived damaged, stale, or wrong.” The
field shows this kind of example while it is empty.

You can also select an **Answer coverage signal** in the activation header.
For example, a routine can be eligible when a request is **Unanswered** because
of **Insufficient evidence**. This is an extra typed condition alongside the
trigger. Normal activation, confirmation, and action permissions still apply;
recognizing a gap alone does not start an external action.

### Reentry

A routine can finish more than once in one conversation. Reentry decides what a
later matching message does:

- **Once per conversation** — the default for one-time tasks such as capturing
  a lead.
- **Every time it matches** — for repeatable tasks such as looking up an order.
- **Let the assistant decide** — the agent chooses whether to resume the run,
  start a fresh one, or leave the completed run in place.

### Expose a routine as a tool

A routine normally starts when its trigger matches what a customer says. An AI
agent calling your agent on a customer's behalf can start it more directly: as a
named tool, with the routine's collected information filled in up front. Open
**Starts when** and switch on **Expose as a tool**, then give the tool a name and
a one-line description that tells a calling agent when to use it.

The name is what the calling agent invokes, so it follows the grammar tool
catalogs expect: 2–63 characters of lower-case letters, digits, and underscores,
starting with a letter — `start_return`, `request_callback`. The editor accepts
whatever you type and reports a name outside that grammar as a validation note,
the same way it reports an unreachable step; Review & Publish refuses the
revision until the name is fixed. Two routines on the same agent cannot share a
name, and the names the MCP surface keeps for itself — `ask_agent`,
`radioso_docs`, `radioso_doc_page`, and `get_conversation_updates` — are refused
as `exposure_tool_name_reserved`.

Once the agent is published with a tool name, that name stays fixed for the
routine — even while you later switch exposure off — so a calling agent never
finds the same routine under two names. A publish that renames it is refused
with `exposure_tool_name_changed`. To offer the routine under a different name,
switch its exposure off and create a new routine with the new name.

A routine whose activation has a gate cannot be exposed: a tool call would start
it without the gate being checked. Such a routine stays reachable through
conversation as before.

### What a calling agent sees

Once the agent is published, a calling agent lists the routine as a tool built
from the information the routine collects. Each declared slot becomes one input:
a text slot is a string, number and yes/no slots keep their types, an email slot
is a string that must look like an address, and a date slot is a string that
must be an ISO calendar day (`2026-09-01`). A slot marked required is required
in the tool; the slot's description travels with it, so a clear description
helps the caller fill it correctly. A routine with no slots is still a valid
tool — a "request a callback" routine needs nothing up front.

A call with values filled in skips the steps that would have asked for them and
lands on the first step that still needs something: a slot the caller left out,
an approval, a skill. From there the routine runs exactly as it does in chat,
and the reply names the routine, where it stopped, and every slot it still
needs. A call that does not match the tool's inputs is refused before the
conversation records anything. Activity shows a tool call as a block with the
tool name and the values it carried. The [calling agent](/guides/agent-converse#routines-as-tools)
guide shows the catalog and the call from the caller's side.

## Collect values and add steps

A value is information the routine collects, such as an order number or email.
In Document, type `@` in an instruction to add a value like `@order_number`.
The routine waits at a step that asks for a value, stores the visitor's reply,
then continues through the flow.

Choose a type — `text`, `number`, `boolean`, `email`, or `date` — in
**Information**, or `item` for a card the visitor picks (see [Show a skill's
results as cards](#show-a-skills-results-as-cards)). Open a value's row there to switch **Required** off when the
flow may reach an ending while the value remains empty, turn on **Editable after
completion** when a visitor may correct it after the routine ends (see [Changes
after a routine ends](#changes-after-a-routine-ends)), or turn on **Sensitive**
when it is something the visitor would not want copied around. Ray switches
**Editable after completion** and **Sensitive** on or off for a value, and only
when you ask.

The type decides what the routine keeps. An email has to look like an address,
a date has to be a real day on the calendar, and a number has to be a number.
When a visitor's answer does not fit — "giulia at example" for an email, "the
31st of February" for a date — the routine keeps nothing for that value and asks
the step again. The turn trace lists the value under `rejectedSlots`, by name
only. The same list can name a value the routine never defined — the model read
more from the visitor's message than any step asked for; it is dropped before
it reaches a step, a skill, or an action.

The `@` menu also lists what the agent already knows about the visitor under
**Visitor context**. Choose **Current page** to place it in a step, and the
step reads the page's URL, title, and language when it runs — enough to write
"If the visitor is on a program page, confirm that is the program they want to
book; otherwise ask which program @program". A host-defined context variable
the agent has enabled appears in the same list. This is a value the step
reads, not one it stores: nothing is added to **Information**, so ask for
anything you want to keep with an `@` slot.

A blank numbered line always sits after the last step — click it to write a
chat step directly. The **+ Step** menu adds chat, skill, approval, and action
steps. A skill step can use a fixed input or a value the routine holds, then
assign its outputs to values that later steps can read. For example, a refund
lookup can use `@order_number` and set `@refund_status` for a later branch.

A chat step's instruction is the controlling instruction for its reply. The
agent's directives still shape how the reply is said — tone, formality, what it
must not claim — but they don't swap the step's question for a redirect or a
hand-off, and they don't add contact details or links the step doesn't ask
for. A step that asks for a name and email asks for them even when an
**Always** directive tells open answers to send booking questions to
reception. See [Directives on a routine turn](/guides/authoring-directives#directives-on-a-routine-turn).

A chat step's reply takes its facts from the step's own instruction, including
any **Visitor context** chip placed in it, and from the sources it has on that
turn: the text of the page the visitor is on, when the step references
**Current page** and the embed sends page content, and the documents a
**Retrieval context** step fetched earlier in the same turn. A chat step
searches no documents itself. When a step says "tell them the edition dates
from the page" and the visitor isn't on a course page, the reply is told it has
no page text and no documents, so it asks the visitor for their dates instead
of stating the course's. A visitor's own dates, such as "I'm free between the
17th and 27th", reach it as the visitor's words, not as a source. Put a fact
every visitor needs in the instruction itself, or in a page or document the
step reads.

### Show a skill's results as cards

When a skill step searches for something — homes to rent, rooms, products — the
chat step after it can show what it found as cards and let the visitor pick one.
Take a letting agency's routine: a step asks for `@area` and `@budget`, a skill
step `search` looks up homes with them, and the next chat step says "Show the
homes within their budget and ask which one they would like to view." Click that
step's **Chat** badge, set **Show results as cards** to `from @search`, and set
**Pick fills** to **New item field**. The routine gets a value
`@chosen_search` of type `item`, and the step row reads "Shows cards from
@search → @chosen_search". A later step can name the home: "Confirm they chose
@chosen_search and ask for their email @email".

On the turn the search runs, the step's reply is written from the records the
skill returned. The agent picks which records become cards, at most ten, and
which of their fields give each card its title, subtitle, picture and link; it
never writes a value onto a card itself. Each card has a **Select** button.
Tapping one fills the `item` value and the routine moves on, the same way an
answered step does. Only the cards the step showed most recently in this run of
the routine count: a tap on cards from an earlier reply, an earlier run, or a
step the routine has already left changes nothing the routine holds, and the
step the routine is on replies. The cards appear only on the turn the search ran:
when the step is asked again later, its reply is text.

An `item` value holds the card the visitor picked: its key, its title, its link,
and up to twelve of the record's own plain fields. Wherever a value is shown as
text — `@chosen_search` in an instruction, an operator notice, the AI summary,
the Test Chat trace — it reads as the card's title, and an operator notice adds
the link. A completion export and the data export carry the whole value. A skill
step without input bindings receives the card's title; a skill input binding
cannot name an `item` value.

A visitor may also answer in words. "The second one", "Villa Rosa" or "the
Altbau flat" fills the value with the same stored card a tap would, link and
fields included, because the routine reads the answer against the cards the step
showed, in the order it showed them. An answer that names none of them fills
nothing, and the step asks again. With **Show cards in replies** off, or on a
channel that draws no cards, such as WhatsApp, voice or email, the step lists the
results in its text as a numbered list, Radioso keeps the list with the reply,
and the visitor's answer is read against it the same way.

Validation checks the binding:

- Only a chat step shows results, from a skill step the routine passes through
  before it (`present_step_not_chat`, `present_source_not_earlier_tool`), with no
  step that waits for the visitor in between, since its results are gone by the
  next turn (`present_source_unreachable`). **Show results as cards** offers only
  the skill steps that qualify.
- A pick fills a value of type `item` (`present_slot_not_item`), and a step lets
  the visitor pick exactly when it names that value (`present_selection_mismatch`).
  With **Nothing, only show**, the cards are shown and nothing is filled.
- An `item` value needs a step that fills it (`item_slot_without_presenting_step`).
  A condition on it tests whether it is present or absent, a skill input binding
  cannot name it, and an exposed routine's tool leaves it out.

Over the API, the binding is the step's `metadata.present`:
`{ "from": "search", "selection": "single", "slot": "chosen_search" }`.
Ray's `prepare_routine_structure` carries it the same way.

### Sensitive values

Say a class-booking routine asks "Any injuries we should know about?" and keeps
the answer in `@injury`. Turn on **Sensitive** for that field, and the answer
stays where the conversation runs: later steps still read `@injury`, and your
team still reads it in the Inbox transcript. Every copy that leaves the
conversation shows it masked:

- The team notice lists the field as `Injury: sensitive, open the conversation
  to read it`, and a `{{slot.injury}}` in its subject or intro reads
  `(sensitive)`. The notice's `Open:` link goes straight to the conversation.
  The notice webhook, a completion export, and an action step's payload carry
  `[redacted]`.
- A skill step with no inputs bound hands the routine's values to its skill with
  `@injury` as `[redacted]`. A skill receives the value only when the step binds
  one of its inputs to `@injury` — the binding shows on the step, so anyone
  reading the routine sees where the value goes. Switching an input to a
  variable never picks a sensitive field for you, and Ray flags a step whose
  skill would receive one as `[redacted]`.
- A Test Chat trace shows `[redacted]`, and **Continue in Test Chat** copies the
  conversation with the sensitive turns withheld and the routine's value as
  `[redacted]`. A branch rule or AI condition that reads `@injury` then sees
  `[redacted]`, so the continued test can branch differently than the
  conversation did.
- The visitor's reply to a step that asks for `@injury` is marked as soon as it
  arrives, and so is every turn after which the routine holds the value. Any
  message sent while that step waits is marked, an off-topic question included,
  so it stays out of Audience Pulse and eval snapshots too. Marked
  turns read as `[redacted]` in the conversation summary, Audience Pulse, a
  notice's AI summary, and an eval snapshot, which also captures the routine's
  value as `[redacted]`. To replay such a turn with a value, run the case with a
  routine start state of your own (see [Evals](/guides/evals)).

Only you mark a field sensitive: Radioso never decides it from the field's name
or the visitor's words, and Ray sets it only when you ask. The model the agent
runs on still reads the value, since it is part of the conversation. A value the
visitor gives while no step is asking for it, before its step or as a correction
after the routine has finished, is marked only when the routine stores it, and
once the routine has ended a later reply that mentions the value is not masked.

### Ask for consent first

Masking keeps a value from travelling. Some values need more: health details,
religious beliefs, and the other special categories of personal data need the
visitor's explicit consent before the routine collects them. That's why every
sensitive field the routine asks the visitor for needs a consent that covers
it, and a routine with such a field no consent covers doesn't publish. A
sensitive field no step asks the visitor for, such as a code a skill looks up,
stays masked and needs no consent, since the visitor never gives it.

As soon as you turn on **Sensitive** for a field a step asks for, the field's
row in **Collected information** reads **Needs a consent before publishing**,
next to an **Add consent** button. That button adds a consent for the field to the **Consents**
section underneath, which is where you write it:

- **Asked before collecting** lists the routine's sensitive fields. Pick the ones
  this consent covers. A field another consent already covers is greyed out,
  since one consent covers each field, and so is one no step asks the visitor
  for, since nothing would ask its consent.
- **If the visitor declines** decides what a no does. **Continue without** runs
  the routine without the covered fields, and **Hand off** ends it and hands the
  conversation to a person.
- The wording comes in one box per language, starting with the agent's default
  language, which every consent needs. Write the text and the two labels, one
  to agree and one to decline, exactly as you want visitors to read them. The
  fields the consent covers sit beside the text, so you can name each one in
  it. **Add a language** adds another box.

You don't place a consent in the flow. Radioso asks it immediately before the
step that collects the first field it covers, and that step reads **Asks consent
first** in the document. Here it comes right before the step that asks about
`@injury`. A routine exposed as a tool leaves covered fields out of its input
schema, because a calling agent can't consent for a person.

Turning **Sensitive** off takes the field out of every consent that covered it,
and removing a field does the same. A note under **Collected information** names
the consent each time. A consent left covering no field doesn't save until you
pick one for it or remove it.

Ray writes consents with you, in your words. Ask it to add a consent for
`@injury` and give it the text and both labels for each language, and it
proposes them exactly as you wrote them, for you to apply. It never writes or
translates consent wording itself: ask without the wording and it asks you for
it.

Through the routine API (`POST /api/v1/agents/{agentId}/routines` and
`PATCH /api/v1/agents/{agentId}/routines/{routineId}`), the routine carries
its consents in a `consents` list. A `PATCH` that leaves `consents` out keeps
them, and an empty list removes them all. For the yoga booking above:

```json
"consents": [
  {
    "key": "health",
    "slotKeys": ["injury"],
    "variants": [
      {
        "locale": "en",
        "body": "To place you in the right class we ask about injuries. Your answer stays with this booking and our instructors.",
        "agreeLabel": "I agree",
        "declineLabel": "No thanks"
      },
      {
        "locale": "de",
        "body": "Damit wir Sie im passenden Kurs einplanen, fragen wir nach Verletzungen. Ihre Antwort bleibt bei dieser Buchung und unseren Lehrkräften.",
        "agreeLabel": "Einverstanden",
        "declineLabel": "Nein danke"
      }
    ],
    "onDecline": "continue"
  }
]
```

- `key` names the consent within the routine: letters, digits, and
  underscores, starting with a letter or underscore. The editor names a new
  consent after the field it starts with.
- `slotKeys` lists the sensitive fields the consent covers, at least one, each
  of them asked of the visitor by a step.
- `variants` holds the wording, one per language. The `body` and the two labels
  are shown exactly as you write them. One variant must be in the agent's
  default language, or in English when the agent has none set.
- `onDecline` is `continue` or `handoff`, the two choices above.

Validation names the consent, field, or step to fix. The editor shows each
note beside the part it's about, and a publish refused for one of them names
it too:

| Code | What it means |
|---|---|
| `sensitive_slot_without_consent` | A field marked **Sensitive** that a step asks the visitor for has no consent covering it. |
| `consent_slot_unknown` | The consent covers a field the routine doesn't declare. |
| `consent_slot_not_sensitive` | The consent covers a field that isn't marked **Sensitive**. |
| `consent_slot_not_collected` | The consent covers a field no step asks the visitor for, so it would never be asked. Remove the field from the consent, or ask for it in a step. |
| `consent_slot_covered_twice` | Two consents cover the same field. Keep it in one. |
| `consent_key_duplicate` | Two consents share a `key`. |
| `consent_missing_default_variant` | No variant is in the agent's default language. |
| `consent_text_invalid` | A `body` or label is blank or too long (8,000 characters for a body, 80 for a label), a `locale` isn't a valid language tag or repeats another variant's, the text holds a `{{…}}` reference, or both labels read the same. |
| `consent_step_mixes_fields` | The consent continues on decline, but the step that collects one of its fields also asks for a field it doesn't cover, so a decline can't skip that step. Ask that field in a step of its own, or hand off on decline. |
| `consent_step_needs_default_exit` | The consent continues on decline, but the step that collects one of its fields has no default exit, so a decline can't skip that step. Give the step a default exit, or hand off on decline. |

A `consent_text_invalid` location points at the field, such as
`consent:health.variants[1].agreeLabel`, and the two step codes name the step,
such as `consent:health.steps.ask_injury`. The checks use the agent's default
language as it is when you save, validate, or publish, so after you change that
language, a consent with no wording in it holds the routine's next publish until
you add some. Visitors keep getting the routine as it was last published until
then, and the same goes for a routine published before it had a consent: these
checks hold its next publish, never the one already serving. An agent bundle
import keeps an imported routine whose sensitive field has no consent in
service, and the new agent's first publish asks for the consent.

### What the visitor sees

When a visitor reaches the step that asks about `@injury`, the agent sends the
consent first, as its own reply: the `body` exactly as you wrote it, with nothing
added around it. The language is the one the agent is answering in, or the one
the visitor's page or browser reports, matched by its exact tag and then by its
base language (`de` serves `de-AT`); otherwise it's the agent's default language.
A regional sibling never stands in, so a visitor writing in `pt-BR` gets the
default language rather than a `pt-PT` variant.

How the two choices appear depends on the channel:

| Channel | What the visitor gets |
|---|---|
| Web chat, the website embed, the REST assistant API | The wording, with your two labels as buttons. |
| Email, WhatsApp, Slack, Test Chat, Ray's test turns | The wording, then each label as a paragraph of its own. |
| Voice, and calling agents (MCP, the agent API, A2A) | Nothing: the routine takes its `onDecline` path straight away and keeps no record. |

Voice asks no consent because a transcript is weak proof and Radioso keeps no
audio of the call, and a calling agent can't consent on a person's behalf.

A click on a button is the visitor's decision, bound to the wording that reply
showed; the label text plays no part. A click on the buttons of an earlier ask,
or a message on a channel that shows the choices as text, counts as a written
answer. The visitor can also answer in their own words, in
any language. The agent reads that as agreement only when it clearly and fully
agrees to the wording shown. A clear refusal takes the decline path.
Anything else, such as "ok", a question about the wording, or a yes with a
condition attached, gets a short answer drawn only from your wording, followed by
the wording and its choices again. If the next reply is still unclear, it counts
as a decline.

The message that agrees never fills a covered field on its own turn, even "Yes,
and I have a sore knee": the step asks about `@injury` next. From there the step
can use what the visitor already said, in that message or before the consent, so
a reply of "no, that's all" keeps the sore knee. Because a reply like that states
the value, it's masked like any message that carries a sensitive field.

A decision holds for the rest of the conversation. The routine doesn't ask again
before another step that collects a covered field, or when it runs again, and a
visitor who switches language isn't asked again either.

Test Chat works the same way across the turns of one test, so you can agree and
then give the covered field. Its decisions stay with the test and never become
consent records: the person answering is you, not a visitor.

On a decline, `continue` runs the routine without the covered fields: a step that
collects nothing else moves on by its default exit, and branch conditions read the
fields as empty. `handoff` ends the routine and hands the conversation to a person
with the reason `routine_consent_declined`. The operator notice says the visitor
declined consent and carries none of the values the consent covers.

### The consent record

Each decision is kept as proof: the decision (`granted` or `declined`), whether
it was a decline after two unclear replies, how it was given (`button` for a
click, `reply` for an answer read from the visitor's message), the language and
the exact wording shown, the channel, the conversation, visitor, agent and
routine, the fields it covers, the message that carried it, and when. It holds
no reply text and no field values. Every
wording shown is kept unchanged, so a record always shows what its visitor saw:
when you edit the wording, later conversations get the new text and earlier
records keep the old.

A record is kept while its conversation exists, then follows your workspace's
conversation retention window, counted from the decision; with no window set, it
lasts as long as the workspace. Erasing a
conversation or a visitor keeps their records and drops only the link to the
message that carried the decision, so you can still show the consent was given.
A data subject's export lists their records under `consent_records`, with the
wording each one was given on. Deleting the workspace removes them.

### Withdrawing a consent

A visitor can take back a consent they gave, and you act on their request
(Article 7(3) of the GDPR). Open the conversation in the dashboard; from the
Inbox, that's **Open in debug view**. The **Consents** panel under the visitor
lists each decision in the conversation with its language, channel and time,
and **Wording** shows the exact text the visitor saw. Owners and admins see
**Withdraw** on a granted consent. Once you confirm:

- The values of the fields the consent covered are erased from the
  conversation's routine state, a routine that already finished included.
- Each message that carried one of them keeps `[redacted]` as its text and
  reads **Withheld after consent was withdrawn** in the conversation, for you
  and for the visitor. Radioso's copies of that message are withheld with it:
  the body and raw copy of the email it came in as, the turn's debug record, the
  coverage assessment's restatement of the question, the picture cards a reply
  showed, and any photo the visitor attached. The conversation's summary and
  title are cleared and written again from what the transcript now reads.
- The record keeps its proof and gains the withdrawal time and the teammate who
  withdrew it. It shows as withdrawn in the panel and in the data subject's
  export.
- A routine still running in the conversation carries on without those fields,
  as it would after a decline, and doesn't ask the consent again.

A message carried a value in two ways. Radioso marks the turns of a routine
that held one, and it also finds every message, the visitor's or the agent's,
whose text contains a value the routine held, ignoring case and spacing. Say a
visitor asked "Do you run classes for a sore knee?" before booking, and the
agent answered "You told me about your sore knee" after the routine ended: both
are withheld with the turns the routine marked. A value shorter than four
characters, a number, or a yes or no would match text that never stated it, so
only the routine's own marks find those. When the step that asks for a covered
field takes the answer from something the visitor said before the consent,
Radioso marks that earlier message right then, so the summary and every other
copy read it as withheld from that turn on.

A declined consent has nothing to withdraw, and a withdrawn one stays
withdrawn. Withdrawal also works over the API: see
[Chat and history](/api/chat-and-history#conversation-history). Conversation
lists in the dashboard refresh on their own; a visitor with the chat open sees
the withheld text once they reload it.

Some copies sit outside what a withdrawal reaches. Text already delivered to
Slack or WhatsApp stays with those providers, and the WhatsApp channel's own log
of what it sent and received keeps its copy until deleting the conversation
removes it.
A value a routine already passed to a skill stays with the service that skill
called, and an email reply still being sent keeps its body until the send
settles. If the agent was answering the visitor at the moment you withdrew, that
turn saves no covered value either, and its two messages are withheld when its
routine marked them or they state a value its routine held; a reply written
outside any routine at that moment keeps its text. Fields are matched by key, so
a field with the same key in another routine of the conversation is erased and
withheld too. Deleting the conversation removes everything Radioso keeps of it.

### Changes after a routine ends

Say a visitor gives an arrival date of 5 January, then tells your booking
routine they're only browsing, and it ends without telling anyone. With
`@arrival` marked **Editable after completion**, "actually I'd arrive on 9
January" updates the date the routine holds, and the agent confirms it noted the
change. It reads "9 January" against today's date, so the year comes out right.

The agent takes a change only when the change is real:

- **The routine holds the value.** A routine that ended before the visitor gave
  a date holds no `@arrival`, so "I'd like to book from 8 to 10 January" is a new
  request, not a change.
- **Nothing the routine collected has left the conversation.** Once its ending
  notified your team, handed off, or sent the completion export, or a skill,
  action, or approval step ran, a changed value would reach none of them. The
  agent takes no change and answers the message like any other. Every skill
  step counts, even one that only looks something up.
- **The visitor is changing what they gave.** A request for something new, such
  as another booking with different dates, is not a change either.

A message that isn't a change goes on as any message does, and the routine's
[reentry](#reentry) setting decides what happens to it. Under **Once per
conversation**, the default, the finished routine doesn't start again, so "I'd
like to book from 8 to 10 January" gets a normal answer. Under **Every time it
matches** it starts a new booking. The agent keeps a finished routine for 30
minutes after its last update; after that, no change is taken.

When a routine can't end without sending what it collected, **Editable after
completion** does nothing on its fields. The field's row says so beside the
switch, and Ray's `validate_routine` reports each such field as
`mutable_slot_not_correctable`. Neither stops the routine from saving or
publishing.

## Set branches, approvals, and endings

Add a condition row beneath a step — the round **+** under its branches, or
**+ Condition** in the step's own editor — to choose its next target: another
step, **Finish**, or **Hand off**. Rows run in order. Use **Rule** for an
exact typed check, skill outcome, filled-value check, or bounded retry. Use
**AI decides** when the agent needs to judge the condition in the
conversation; type `@` in the condition box to reference a collected value.

An approval step pauses the routine for a workspace member. Add it with
**+ Step**, name the decision, then give each choice a label and target. The
initial **Approve** and **Decline** choices suit many flows; a choice such as
**Ask for receipt** can direct the flow to collect more information. The selected
choice continues along its decision edge.

An ending row completes the routine with **Finish** or escalates it with **Hand
off**. Set a message on the ending the agent should deliver. Named endings let
different paths provide different completion messages. A **Hand off** ending
also sends the operators the routine's name and every value it collected, by
email, the contact webhook, and Slack, so the person picking the conversation
up starts with what the visitor already said.

A **Finish** ending can send that same notice while the agent keeps the
conversation. Open the ending and turn on **Notify the team**: a booking
routine then tells reception about the booking, and the agent goes on to ask
whether there is anything else it can help with. The switch stays on for a
**Hand off**, which always notifies. **Subject** and **Intro** are optional —
type `@` to insert a value the routine collects, as in
`New booking: {{slot.guest_name}}`; a subject holds up to 200 characters and an
intro up to 2,000.
Blank fields use the default subject, such as `Book accommodation: completed`,
and every notice lists all the collected values below the intro, so a short
subject never hides what the guest said. A value the routine did not collect
shows as `—`. The webhook body is documented under
[Operator notifications](/api/agents-and-skills#operator-notifications).

Turn on **Include AI summary** when the team also needs relevant context the
routine did not collect in a field. Radioso generates it after the ending has
queued its notice, keeps the collected values as the authoritative record, and
labels the extra section **AI summary**. If generation cannot finish, the notice
still sends without that section.

Under **Notify the team**, the **Send with** select chooses which notify
skill delivers the notice: **Default**, or any enabled notify skill the
routine can name directly. The line underneath shows where that choice goes
right now — Valmora's booking routine names its `notify_bookings` skill on the
**Booked** ending, so the line reads `Sends to marta@valmora.example (waiting for confirmation)` until Marta uses the confirmation link. Confirmed addresses have no suffix; grandfathered, revoked, and bounce- or complaint-suppressed addresses carry their own status beside the address. Choosing **Default** falls
back to the chain above: the line then shows the `contact_human` recipients,
the agent's own delivery setting, or the workspace owner's email, whichever
resolves first. A **Hand off** ending offers the same select, since it always
notifies.

**Replies go to** picks the email field whose address reception's reply goes
to: any of the routine's email fields, or **No reply-to**. With
`guest_email` chosen on Valmora's **Booked** ending, Marta hits Reply and
writes straight to the guest. Radioso uses only the field you pick — a gift
booking that collects the buyer's address and the recipient's is answered at
whichever one you chose. A notice you turn on, or a new **Hand off** ending,
starts on the routine's only email field when there is exactly one, and on
**No reply-to** when there are several. A guest who never gave that address
gets a notice with no reply-to.

When the routine has an email field and a notifying ending's **Replies go
to** is **No reply-to**, a note under the select reads "Replies won't reach the visitor.
Choose their email field." The ending still saves and the routine still
publishes, so a routine with nobody worth replying to stays as it is.

The first five contact or team-notice dispatches in a conversation are
eligible for delivery. After that, Radioso records a
`conversation_dispatch_cap` outcome and skips the dispatch. Email recipient
attempts also count against the workspace's daily plan allowance; reaching it
records `workspace_daily_email_cap` and leaves a configured webhook active.
An external address must confirm within its workspace before it receives a
notice. Adding it to a notify skill sends the confirmation message right away,
so Marta can confirm before the first booking arrives. An address configured
before confirmation existed keeps receiving notices and gets the confirmation
message with its first one; it has 14 days from that message, and at least
until its recorded deadline, to confirm. Every notice carries a
one-click unsubscribe link, and a hard bounce or complaint suppresses
notification mail to that address across the deployment. When the workspace's
daily email allowance stops a notice, a line under the destination says so; the
allowance resets at midnight UTC, and a configured webhook still receives the
notice.
Routine slot text is capped at 1,000 characters before it reaches either
delivery, and a collected reply-to is used only when it is a valid email
address.

A step is asked the same way at most three times in a row when the visitor's
replies give it nothing new. From then on it asks in different words, saying
plainly what it needs and giving an example of an answer that works. The limit
never fires a row you set: a **Hand off** row may be the step's confirmation, and
taking it would send a request the visitor never confirmed.

What comes next depends on whether the routine hands off at all. When some row
leads to a **Hand off** ending, a visitor who still gives the step nothing after it
asked differently goes to a person. The routine ends on that step, tells the
visitor someone will continue the conversation, and notifies your operators with
the reason `routine_stuck` and every value collected so far. The **Hand off**
ending's message and the completion export stay for visitors who reach that
ending. A routine with no **Hand off** ending stays on the step until the visitor
answers it. To give a visitor an earlier way out of a step that collects something
hard to get right — a booking reference, an exact date — add a row for it, such as
**AI decides** "the visitor wants to talk to a person" → **Hand off**.

## Validation and publishing

The editor validates as you work. A routine is one of the agent's scoped editable
areas, alongside directives, skills, and context variables. All four
share one publication boundary: **Review & Publish** on the agent snapshots them
together into a revision, and that revision serves conversations. So an edit
changes what the agent will run after the next Review & Publish, and nothing
before it.

A conversation keeps the revision it started on. A visitor part-way through a
routine finishes on the version they began with, while you work on the next one.

Each routine also carries an enabled flag — the **Draft**/**Live** pill in its
header. Switch a routine to **Draft** to take it out of play while keeping
everything you built — useful for comparing agent behavior with and without
it, or parking a flow you are still working out.

## Try a routine before it ships

Choose **Test** to open the agent's **Test Chat** with the draft selected.
The draft holds the routine you are editing alongside the rest of the agent's
unpublished work, so the routine runs turn by turn in that conversation exactly
as a publish would ship it, then returns to normal answering when it finishes.
The routine has to be **Live**: one still marked **Draft** sits outside the
draft's activation set, so **Test** is disabled until you switch it over.

In **Test Chat**, you can also compare the draft with the published revision and
run selected eval cases. Switching which version you test starts a fresh test
conversation, so routine state from one cannot mix into the other. Evals are
optional evidence for the publish decision.

Use the test to check the trigger, information collection, skill bindings,
branches, endings, and handoffs before you publish the agent.

A private test keeps skills with outward effects off by default, so nothing
sends to a real customer while you work. A tool step that calls an external
MCP tool, a webhook, or a customer email or Slack skill reports `failed` with
the reason *skills are off in this test*, and the routine takes its failed
branch, so you can watch that path too. Choose **Run skills for real** in the
Test Chat actions menu to start a fresh private test where every skill runs
exactly as it would for a customer. Retrieval skills run in both modes, and
test values still stand in for context variables either way. Action steps,
handoffs, team notices, and completion export stay off in every private test;
a test turn that reaches an ending that notifies shows the notice it would
send, and the address replies would go to, in the turn's trace instead.

A notify skill delivers through the saved conversation, so it stays off in
every private test even with **Run skills for real** on. **Retry** re-runs
the turn, so a skill the first attempt already fired fires again. **Run
evals** always replays with skills off, and you can only capture an eval case
from a test that kept skills off.

## Common failure modes

- A routine fails to start: the trigger describes the wrong situation, or a
  higher-priority routine claims the turn first. Test the trigger with
  **Test**.
- A coverage condition does not activate: inspect the originating turn. A
  failed or unavailable assessment is recorded as not assessed and never
  activates a coverage condition.
- A step that shows results as cards replies in plain text: the agent's **Show
  cards in replies** is off, the channel draws no cards, the skill failed or
  returned nothing, or the search ran on an earlier turn. Cards appear on the
  turn the search runs.
- A step skips value collection: add the value with `@` in the instruction so the
  step refers to the stored information.
- A step's reply carries text from a directive: directives shape every routine
  reply. The turn trace lists them under `routineStep.steeringDirectives` on the
  `directive_steering` stage; narrow or turn off the directive when its wording
  does not belong in the flow.
- A backward jump fails validation: set **Max N** so the loop has a bounded
  number of passes.
- A routine never starts at all: check that its pill reads **Live**, not
  **Draft**.
- A team notice shows `—` where a value belongs: the ending's subject or intro
  references a value the routine did not collect on that path. Collect it in an
  earlier step, or drop it from the notice text.
- A finish sends no team notice: check that **Notify the team** is on for that
  ending, and that the agent has a contact recipient — the notice goes where
  contact requests go.
- The **Send with** select shows a name as **(unavailable)**: the notify skill
  it names was deleted, turned off, or can no longer be named by a routine.
  Validation flags the ending until you pick another skill or switch back to
  **Default**. The notice is never dropped meanwhile: a skill that still exists
  and is on keeps sending, and otherwise the notice goes to the default
  destination, or to the agent's contact settings or the workspace owner when
  `contact_human` is off.
- The **Replies go to** select shows a field as **(not an email field)** or
  **(sensitive)**: its type changed, or it was marked sensitive, after you picked
  it. A sensitive address never leaves the conversation, so it can't take
  replies. Validation reports `operator_notice_reply_to_slot_invalid` until you
  pick another email field or **No reply-to**.
- A visitor's change after the routine ended isn't taken, though the field is
  **Editable after completion**: the routine held no value for it, or its
  ending already notified the team, handed off, or exported, or a skill,
  action, or approval step ran. The turn's span records why as
  `routine.slot_correction.decision` (`not_held`, `already_sent`, or
  `new_request` when the message asked for something new). When every way
  through the routine sends what it collected, `validate_routine` flags the
  field as `mutable_slot_not_correctable`.
- A booking request after a booking routine ended gets a normal answer instead
  of a new booking: the routine runs **Once per conversation**. Set its reentry
  to **Every time it matches** to let it start again.
- A webhook or Slack skill receives `[redacted]` for a value: the field is
  marked sensitive and the step passes it without a binding. Bind the skill's
  input to the field on the step, or turn **Sensitive** off.
- Reception's reply goes nowhere useful, or the email has no reply-to: check
  **Replies go to** on that ending, and that the routine asked for that field
  on the path the visitor took. The editor shows a reminder under the select
  whenever a notifying ending has an email field available and none chosen —
  it never blocks saving, so a routine can ship with the reminder still
  showing.
- Review & Publish refuses the agent with `exposure_tool_name_changed`: a
  published tool name is fixed. Keep the name, or switch exposure off and create
  a new routine under the new name.

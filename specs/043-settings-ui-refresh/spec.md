# Feature Specification: Settings UI Refresh

**Feature Branch**: `[043-settings-ui-refresh]`  
**Created**: 2026-04-19  
**Status**: Approved  
**Input**: User description: "examine how radioso settings ui works, suggest your changes, get approved by plan-ceo-review, then agent-senior-engineer can implement"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Navigate settings by job to be done (Priority: P1)

A workspace operator opens Settings and can immediately tell where to go for workspace identity, public access, ingestion tuning, retrieval tuning, and connector setup without scanning a long undifferentiated page.

**Why this priority**: The current settings experience makes orientation too expensive. Fixing the information architecture is the highest-leverage improvement because it reduces friction across every other settings task.

**Independent Test**: Open the settings area on desktop and mobile, switch between tabs, and confirm each tab exposes a visible summary plus a section index that jumps to the relevant section without losing context.

**Acceptance Scenarios**:

1. **Given** an operator opens Settings, **When** the screen renders, **Then** each tab presents a short purpose statement and a visible list of its sections.
2. **Given** an operator wants a specific section such as website embed or metadata rules, **When** they select that section from the local settings index, **Then** the page scrolls to the matching section and keeps the URL anchor aligned with the destination.

---

### User Story 2 - Tune retrieval and ingestion without decoding the implementation (Priority: P2)

An operator tuning chunking or retrieval should understand what each group of controls does, what stage it affects, and where to save changes without mentally reconstructing the backend pipeline.

**Why this priority**: Retrieval and ingestion are the highest-complexity tabs, and the current UI exposes raw parameters before giving the operator a strong model of what each group changes.

**Independent Test**: Open the ingestion and retrieval tabs, verify the settings are grouped into compact sections with clear headings and section summaries, and confirm the save affordance remains visible while scrolling through long forms.

**Acceptance Scenarios**:

1. **Given** an operator opens Ingestion, **When** they review the page, **Then** strategy selection, active strategy tuning, and reprocessing are presented as distinct sections with concise explanatory copy.
2. **Given** an operator opens Retrieval, **When** they review the page, **Then** query rewriting, search tuning, metadata rules, and answer behavior are separated into scannable groups with persistent save access.

---

### User Story 3 - Manage general settings in coherent groups (Priority: P3)

An operator managing workspace details, API access, assistant identity, anonymous chat, and website embed should see those controls grouped by purpose rather than as a long stack of unrelated blocks.

**Why this priority**: General settings currently mixes organization, security, assistant identity, and embed configuration in one long flow. Grouping and hierarchy fixes operator confidence and editing speed.

**Independent Test**: Open the General tab and confirm workspace/access settings, assistant setup, anonymous chat, and website embed each appear as clearly separated sections with consistent card styling and save behavior.

**Acceptance Scenarios**:

1. **Given** an operator opens General settings, **When** they scan the page, **Then** the sections appear in a clear order from core workspace setup to external/public channels.
2. **Given** an operator updates assistant identity or website embed settings, **When** they scroll through the page, **Then** the section structure and save controls remain easy to find without re-reading unrelated settings.

### Edge Cases

- What happens when a settings tab has no anchor in the URL or the anchor does not match any current section?
- What happens when the local settings index is used on narrow screens where the page becomes single-column?
- What happens when a long metadata rules list expands beyond the viewport?
- What happens when save actions are disabled because there are no changes yet?

## Constitution Constraints *(mandatory)*

- Implementation MUST NOT begin until this spec is approved.
- Work MUST NOT start without a written, approved spec.
- Backend MUST be implemented in Node.js and frontend MUST be implemented in React.
- Database MUST be PostgreSQL with `pgvector` for embeddings and vector search.
- LLM integrations MUST use GPT-5.2 as the default provider.
- User-facing assistant or chat responses MUST NOT rely on hard-coded application strings; runtime conversational copy MUST be generated by the LLM so multilingual behavior remains intact.
- Backend development MUST follow TDD: tests written and failing before implementation.
- Secrets and keys MUST be stored in `.env` and never committed; `.env.example` MUST be updated.
- Customer data MUST be protected with least-privilege access and secure transmission.
- Admin-facing pages MUST use the shared dark theme and existing design tokens.
- Features MUST preserve modular boundaries between transport, orchestration, domain logic, and persistence.
- Specs MUST identify files or modules that should remain responsibility-limited rather than absorb new concerns.

## Architecture Constraints *(mandatory)*

- **Boundary Rule**: `frontend/components/dashboard/settings-view.tsx` owns top-level settings routing and tab switching; tab panels own tab-specific composition; reusable settings layout primitives live under `frontend/components/dashboard/settings/`.
- **Encapsulation Rule**: `general-tab.tsx`, `retrieval-settings-panel.tsx`, and `ingestion-settings-panel.tsx` must remain panel composition files rather than absorb shared navigation or layout logic inline.
- **New Seams Required**: Introduce focused settings layout/navigation helpers and tab metadata helpers so the redesign does not duplicate structure across panels.
- **Anti-Goals**: Do not change backend settings contracts, do not add new persisted settings, and do not replace the existing design system or dark theme tokens.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: System MUST present each settings tab with a short tab-specific overview and a visible section index that links to sections inside that tab.
- **FR-002**: System MUST support deep-linking to settings sections through the existing settings anchor route state.
- **FR-003**: System MUST reorganize the General tab into coherent groups for workspace/access, assistant setup, anonymous chat, and website embed.
- **FR-004**: System MUST reorganize the Ingestion tab into distinct sections for strategy choice, active strategy tuning, and existing-document reprocessing.
- **FR-005**: System MUST reorganize the Retrieval tab into distinct sections for query rewriting, search tuning, metadata rules, and answer behavior.
- **FR-006**: System MUST keep save actions visually accessible while operators scroll long ingestion and retrieval forms.
- **FR-007**: System MUST remain usable on mobile and desktop without breaking current settings functionality.
- **FR-008**: System MUST reuse existing settings APIs and existing settings values without contract changes.
- **FR-009**: System MUST add frontend verification for the settings navigation metadata and anchor behavior introduced by this redesign.
- **FR-010**: System MUST update operator-facing settings documentation that explains the new page organization when applicable.

### Key Entities *(include if feature involves data)*

- **Settings Tab Descriptor**: Frontend-only metadata describing a tab title, summary, and the sections available inside that tab.
- **Settings Section Descriptor**: Frontend-only metadata describing a section anchor, label, and optional helper copy used for local navigation and layout.
- **Sticky Save State**: Frontend-only state that decides when tab-level save controls are shown and whether they are enabled.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: A first-time operator can identify the correct settings section for a named task in one navigation step from the tab landing view.
- **SC-002**: Retrieval and ingestion save actions remain visible without scrolling back to the top on standard desktop viewport heights.
- **SC-003**: The redesigned settings pages preserve all current settings behaviors with no API contract changes.
- **SC-004**: Frontend tests cover the new settings navigation metadata and anchor behavior introduced by the redesign.

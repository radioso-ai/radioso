# Workspace event log

The workspace event log tells an automation that something happened: a visitor started a conversation, left their contact details, was handed to a person, finished a routine, or is waiting on a decision, and a document finished processing or failed to. Each event carries the ids and values an automation acts on, so a row lands in a sheet or a lead appears in a CRM without anyone copying it across.

Read it with a personal token or a service-account credential that holds `workspace.events.read`. Every role that reads history holds it.

To have each event sent to a URL as it happens instead of polling for it, use [workspace event subscriptions](/api/workspace-event-subscriptions). A push carries the same event this log lists.

## How it works

1. Call `GET /api/v1/workspace/events` without a cursor. You get the newest events, oldest first, and a `nextCursor` that points at the end of the log.
2. Store `nextCursor`. On your next poll, send it back as `after` and you get everything that happened since, oldest first.
3. Keep the `nextCursor` from every response, even an empty one. It moves forward on its own, so a quiet log costs one cheap request.

This calls the hosted EU API; use `https://api-us.radioso.ai` or your own self-hosted origin instead, matching the host where the credential was issued.

```bash
curl -sS "https://api.radioso.ai/api/v1/workspace/events?types=contact_request.created,routine.completed" \
  -H "Authorization: Bearer $RADIOSO_API_TOKEN"
```

```json
{
  "events": [
    {
      "id": "6f1c2d4e-8a90-4b1c-9d2e-3f4a5b6c7d8e",
      "type": "routine.completed",
      "version": 1,
      "occurredAt": "2026-11-19T14:02:11.482Z",
      "workspaceId": "4d7293c8-d241-4f8f-a4db-3df5b88da44c",
      "data": {
        "conversationId": "0b9e6a52-6c1f-4a8e-9f3d-2c7b1e5d4a90",
        "agentId": "a3f0c9d1-2b4e-4f6a-8c7d-9e0f1a2b3c4d",
        "channel": "website_embed",
        "callerKind": "human",
        "visitorId": "c81d4e2a-7f3b-4c9e-a1d5-6b2e8f0c3a7d",
        "routineId": "table-booking",
        "executionId": "5e2d9c1b-3a4f-4e8d-b7c6-1f0a9e8d7c6b",
        "outcome": "complete",
        "values": { "name": "Ada Example", "partySize": 4, "phone": "[redacted]" },
        "sensitiveSlotKeys": ["phone"]
      }
    }
  ],
  "nextCursor": "eyJ2ZXJzaW9uIjoxLCJrZXlzIjp7InR4IjoiOTQ4MjEi...",

```

`types` narrows the list to the types you name, comma-separated. Leave it out and you get every type you may read. A cursor belongs to the `types` it was issued for: send it with the same filter, or start again without one.

`limit` takes 1 to 100 and defaults to 50. When `hasMore` is `true`, more events are waiting right now: send `nextCursor` again straight away.

## Paging never skips an event

Two turns can write events at the same moment and finish in either order. The log holds an event back until every transaction that started before it has finished, so an event that commits late still arrives after your cursor instead of behind it. Usually that wait is too short to notice. A write that runs long, such as a database migration during a deploy, delays newer events until it ends; nothing is lost.

Deduplicate on `id` when your automation might read the same page twice, for example after it crashed before storing `nextCursor`.

## Event types

Every event has the same envelope: `id`, `type`, `version` (the version of that type's `data` schema), `occurredAt`, `workspaceId` and `data`.

### Conversation events

A conversation event's `data` starts with the conversation it is about: `conversationId`, `agentId`, `channel`, `callerKind` (`human` or `agent`) and `visitorId`. `agentId` and `visitorId` are copies taken when the event was recorded, so they keep the ids they had then.

| Type | Recorded when | What `data` adds |
|---|---|---|
| `conversation.started` | A conversation is created, which happens with the first message a person or calling agent sends. Opening the chat widget or showing its greeting records nothing. | Nothing beyond the conversation. |
| `contact_request.created` | A visitor leaves contact details through a contact request. | `contactRequestId`, the queued request's stable id, and `values`: what the visitor gave, keyed by field, such as `email` and `message`. When a routine's step queued the request, `values` holds the routine's slots only. |
| `handoff.requested` | The agent hands a conversation to a person. | `reason`, the handoff reason code (see below). |
| `routine.completed` | A routine run ends, whichever way it ends. | `routineId`, `executionId`, `outcome` (`complete`, `handoff`, `action`, `stuck` or `consent_declined`), `values` (the routine's declared slots) and `sensitiveSlotKeys`. A visitor who corrects a value after the run ended records the run again, with the corrected values and the same `executionId`. |
| `decision.pending` | A routine stops at a decision step and waits for a teammate. A teammate decides in the Inbox: the event tells an automation the decision is waiting. | `decisionHandle`, `routineId`, `stepId`, `reason` (the text the routine's author wrote on the step), `options` (`id` and `label`) and `deadline`. |

A slot the routine's author marked sensitive reads `[redacted]` in `values`, as it does in every notice and export, and so does a notify step's input bound to one. `sensitiveSlotKeys` names a routine run's masked keys.

A handoff's `reason` is one of these codes:

| Code | Why the conversation went to a person |
|---|---|
| `routine_handoff` | A routine reached a hand-off ending. |
| `routine_stuck` | A routine's step stayed unanswered past its re-ask limit. |
| `routine_consent_declined` | The visitor declined a routine's consent, and its decline choice hands off. |
| `retrieval_miss` | The agent found nothing to answer from and hands off on a miss. |
| `operator_takeover` | A teammate took the conversation over. |
| `operator_only_mailbox` | The conversation arrived at a mailbox only teammates answer. |
| `generation_budget` | The channel's budget for generated replies ran out. |
| `review_unavailable` | A reviewed turn could not produce a reply to review. |
| `policy_changed` | A mailbox's settings changed under a draft the customer was waiting on. |

The contact details and routine values an event carries are the ones an automation acts on. To read the whole conversation, use [conversation history](/api/chat-and-history#conversation-history): `GET /api/v1/history/chat/{conversationId}` with a credential that holds `workspace.history.read`.

No event carries a transcript or the agent's reply.

Conversations a teammate runs to test an agent (Test Chat, workbench replays, Ray's test turns) record no events, as they stay out of history's lists.

### Document events

A document event's `data` names the document revision it is about:

- `documentId` and `revision`.
- `title`, a copy taken when the event was recorded. An uploaded file's title comes from its file name.
- `contentKind`: `inline_text` for text, `uploaded_file` for a file.
- `sourceKind` and `sourceId`: the document source it belongs to. `sourceKind` is `website` for a crawled site, `connector` for a synced connector, `upload` for the workspace's uploads (every uploaded file belongs to it) and `api` for an API source. Both are `null` for a document with no source, such as text added by hand.

| Type | Recorded when | What `data` adds |
|---|---|---|
| `document.processed` | A document revision finishes processing and is ready for retrieval. Each revision records it once, however many times its processing was retried. | Nothing beyond the document. |
| `document.failed` | Processing a document revision fails and the document shows as failed: on an error a retry cannot fix, or after its last retry. Each failed attempt records one. | `failureCode`: the error code, such as `provider_misconfigured`, or `null` when the failure carried none. The failure message stays on the document, as its `failureReason`. |

A failed revision can still succeed. When a workspace fixes the provider credential that failed it, Radioso queues the document again at the same revision: you get `document.failed` and then `document.processed` with the same `documentId` and `revision`, or a second `document.failed` if it fails again. Treat the latest event for a revision as its state.

A changed or reprocessed document is processed again as its next `revision`, so it records `document.processed` again. Some actions process many documents at once and record one event for each:

- a website crawl or a connector sync, for each page it adds or changes, which on a large site is hundreds of events from one sync;
- reprocessing every document from Settings, reprocessing a whole source, or a reprocess Ray prepares with `prepare_document_reprocess`, for each document it queues.

Changing a document's metadata through its retrieval settings processes that document again too. Filter on `sourceKind` or `sourceId` to follow one kind of source or one source, and on `contentKind` to follow uploaded files.

```json
{
  "id": "0d6c4b1e-2f3a-4c5d-8e9f-1a2b3c4d5e6f",
  "type": "document.failed",
  "version": 1,
  "occurredAt": "2026-11-20T09:14:52.106Z",
  "workspaceId": "4d7293c8-d241-4f8f-a4db-3df5b88da44c",
  "data": {
    "documentId": "9a8b7c6d-5e4f-4a3b-9c2d-1e0f9a8b7c6d",
    "revision": 2,
    "title": "Price list",
    "contentKind": "uploaded_file",
    "sourceKind": "upload",
    "sourceId": "5e1c9a7b-3d2f-4b8e-a6c4-0f9d8e7c6b5a",
    "failureCode": "provider_misconfigured"
  }
}
```

To read the document itself, use [documents](/api/documents-and-search): `GET /api/v1/document/{documentId}` with a credential that holds `workspace.documents.read`.

## Who can read what

The log shows a type only to a caller who may read the same facts elsewhere:

- `workspace.events.read` lets a credential list the log at all.
- Every conversation type also needs `workspace.history.read`.
- `decision.pending` also needs `workspace.conversation.takeover`, as the Inbox's decisions do. It is a notification: listing and resolving decisions are dashboard actions, so an API token that reads `decision.pending` can neither list nor resolve the decision over the API. A teammate acts on it in the Inbox.
- Every document type needs `workspace.documents.read`, as reading the document does.

Without a `types` filter you get the types you may read. Naming one you may not read returns `403` with `event_type_not_permitted`.

## How long events are kept

The log keeps an event for 30 days. A document event goes sooner when its document does: deleting the document, deleting its source, or a sync that removes the page removes its events in the same step, because a title can name a person. A conversation event goes sooner when its conversation does: deleting a conversation, erasing a visitor, or the workspace's own [conversation retention](/operators/data-retention) removes its events with it. When a visitor [withdraws a routine consent](/guides/authoring-routines#withdrawing-a-consent), the conversation's `routine.completed` events for that routine and its contact requests that name a covered field are removed, with any other of its events that states one of the values.

A cursor stays usable for 29 days. An older one returns `410` with `cursor_expired`, because events after it may already be gone: start again without a cursor.

## Common failure modes

| Response | What happened | What to do |
|---|---|---|
| `400` `cursor_filter_mismatch` | The cursor was issued for a different `types` filter. | Send it with the filter it came from, or start again without a cursor. |
| `400` `invalid_cursor` | The cursor is truncated or was not issued by this log. | Send back `nextCursor` exactly as you received it. |
| `400` with `types` in the details | A name in `types` is not an event type. | Check the spelling against the table above. |
| `403` `event_type_not_permitted` | The credential cannot read one of the requested types. | Use a credential whose role holds the permission, or drop the type. |
| `410` `cursor_expired` | The cursor is older than 29 days. | Start again without a cursor. |

# Connect a calling agent

Another AI agent can hold a conversation with one of yours and act on what comes back. It sends a message through `ask_agent`, or calls a routine you have exposed as a named tool, and gets a structured reply envelope beside the prose: what the answer covered, who owns the conversation, and where a routine landed. That envelope is what lets a calling model decide its next move instead of parsing sentences. A client that speaks A2A reaches the same agent over JSON-RPC, [covered below](#connect-an-a2a-client).

Start with [MCP server](/guides/mcp-server) to issue the credential and point a client at the server, or with [Publish and open an agent](/guides/publish-an-agent) if you want callers to reach the agent with no credential at all. This page covers what the client does once it is connected.

## Share an open connection

When **Allow connecting without a credential** is on, **Channels → MCP** includes **Share with agent developers**. Copy the agent endpoint or its discovery card into your own developer guide, or copy one of the Claude, ChatGPT, Cursor, or OpenAI Responses API examples. The examples contain the public id in the URL and no secret; they work only while open access remains enabled.

The discovery card is useful when a caller first needs to learn what the agent does and which routine tools it exposes. The endpoint is useful when the caller already knows which agent it needs. If you turn open access off, issue an MCP credential from the same card and give the developer the credential-specific configuration instead.

## Agent converse setup

The dashboard credential is bound to one agent and the MCP audience. Send its original secret to standalone `/mcp`; the server exchanges it for a short-lived session token. If a process restarts or its cache expires, it exchanges the original credential again and the backend resumes the conversation mapped to that credential version in PostgreSQL. A session token returned by the internal converse endpoint is for direct calls to that endpoint, not for `/mcp`. Revoke the credential from the dashboard when the client should lose access; the server re-checks credential state for every request.

The converse surface provides **`ask_agent`**, which sends a message through the agent's full turn loop and continues its conversation. Retrieval can participate in that turn when the agent's configuration calls for it. Direct document search and grounded-answer generation remain REST API workflows.


## What `ask_agent` returns

The tool's text content is the agent's answer followed by the reply envelope as JSON; its `structuredContent` is that **agent reply envelope** alone, so a calling model can act on the outcome instead of guessing from prose:

```json
{
  "conversationId": "5f3c…",
  "answer": { "text": "You can return an order within 30 days of delivery.", "citations": [] },
  "answerCoverage": { "availability": "assessed", "coverage": "answered", "reason": "sufficient_evidence", "originatingTurnId": "c3…", "originatingRequestId": "c3…" },
  "ownership": { "state": "ai_owned", "suppressed": false },
  "routine": { "name": "Book a demo", "status": "waiting_for_input", "pendingInput": [{ "key": "email", "type": "email", "required": true }] },
  "traceId": "d4…"
}
```

- `answerCoverage` is the same coverage verdict the dashboard trace shows: `coverage` is `answered`, `partial`, `unanswered`, or `unclear`, and `reason` explains it. `availability: "not_recorded"` means no assessment ran for that turn.
- `ownership` says who owns the conversation. `human_owned` with `suppressed: true` means a person has taken over and the agent generated nothing on this turn; [come back for the reply](#come-back-after-a-handoff).
- `routine` is present when the turn touched a routine: the one it ran, or one waiting for an operator's approval. `status` is `active`, `waiting_for_input`, `waiting_for_approval`, `completed`, or `abandoned`; `pendingInput` lists every required slot still open plus the current step's optional ones, each with `key`, `type`, `required`, and `description`, so the client can supply all of them in one message.
- `invocation` is present only on a routine tool call (next section): `toolName` plus an `outcome`.
- `traceId` is the turn's trace id, the one an operator sees in Activity.

The REST agent channel, `POST /api/v1/agents/{agentId}/chat`, returns the same `answerCoverage`, `ownership`, `routine`, `invocation`, and `traceId` fields beside its `answer` string and `citations` array. Both routes publish the envelope as `AgentReplyEnvelopeCore` in the OpenAPI document.

## Routines as tools

A routine an operator has [exposed as a tool](/guides/authoring-routines#expose-a-routine-as-a-tool) is listed for the session by `GET /api/v1/mcp/converse/tools`, one `AgentToolDescriptor` per routine with a JSON Schema `inputSchema` built from the routine's declared slots. A direct converse client invokes it by sending `routine` instead of `message` on the ask route:

```json
{ "routine": { "toolName": "start_return", "input": { "orderId": "A-1001" } } }
```

The routine starts with those slots filled and walks past the steps they satisfy. On that turn the input is its only source of values: it stops on the first step whose required slots the call left out (or, on a step that collects only optional slots, any of its slots), runs nothing after that step, skill steps included, and lists what that step still needs in `pendingInput`. A step moves on once its required slots have values, so an optional slot beside them stays empty unless the call gives it. The caller supplies a missing value in a follow-up message or a second call. The reply reports where the routine landed in `routine` (`toolName` names the tool) and what the call did in `invocation.outcome`: `started`; `reentered` (a completed routine started again, as its reentry setting allows); `declined` (completed under **Once per conversation** — the turn answers normally and `routine` still reports `status: "completed"`); `not_started` (a routine, the one called or another, was mid-flight or awaiting approval and kept the turn; an active routine reads the call as it reads any message, which is how a second call fills what the first left out — `routine` describes it); or `unknown_tool`. Input is validated before anything is recorded: an unknown tool returns `404` with `error.details.code` `routine_tool_unknown`; mismatched input returns `400` with `error.details.code` `routine_invocation_invalid` and one `{ path, code }` entry per field in `error.details.errors` (`required`, `type`, `format`, `unknown_field`, `too_long` over 2000 characters; a blank string counts as missing). Both routes check the tool name against the release the conversation is pinned to, while `GET /api/v1/mcp/converse/tools` lists the current published catalog, so a routine exposed after the conversation began can be listed yet answer `routine_tool_unknown`.

An MCP client gets the same catalog as tools. The standalone server reads it once, when it exchanges the credential for a session, and pins the result, so the session's `tools/list` is stable for its lifetime: `ask_agent`, the two documentation tools, and one tool per exposed routine — `start_return(orderId, reason?)` above — each carrying the operator's description and the descriptor's JSON Schema. Calling a routine tool checks the arguments against that schema first (a miss is a tool error before the backend is involved, audited with the tool name only), then runs the invocation above. The result's `structuredContent` is the full envelope and its text content is `answer.text` followed by that envelope as JSON, exactly as for `ask_agent`.

A routine exposed, renamed, or withdrawn after the session opened appears when the client's next session is established; the server sends no `notifications/tools/list_changed`.

The converse session does not grant access to other agents, workspace administration, account management, API-access settings, Ray, the skill catalogue, connector secrets, or provider keys.

## Come back after a handoff

When a turn hands off to a person, `ownership.state` becomes `human_owned` and the agent stops answering. A calling agent cannot sit in the chat, so it comes back: `get_conversation_updates({ cursor, waitMs })` returns what has happened since your cursor, and waits for it.

```json
{
  "messages": [{ "id": "9a…", "author": "human", "createdAt": "2026-09-22T10:14:02.117Z", "text": "I have refunded the order." }],
  "cursor": "eyJ2ZXJza…",
  "ownership": { "state": "human_owned" }
}
```

`author` is `human` for a person's reply, `agent` otherwise. The cursor is opaque: pass back the one the last reply gave you; with none, the call returns the most recent page. The page reports ownership as a state alone — `suppressed` is a fact about a turn, and a read runs none. `waitMs` holds the call open for up to 25 seconds and returns an empty `messages` list at the deadline — nothing new yet, not a failure. Poll again with the same cursor.

Over standalone MCP the session must survive between calls. The server returns an `Mcp-Session-Id` header on first contact; echo it on every later request to stay in the same conversation. A client that drops it gets a fresh conversation each call.

## Connect an A2A client

A client that speaks [A2A](https://a2a-protocol.org) v1.0 reaches the agent over JSON-RPC, with no MCP client and no Radioso-specific code. It reads the agent's card, sends a message, and gets back either an answer or a task that tracks a routine or a handoff. The agent needs a [public id](/guides/publish-an-agent#the-agents-public-id); the examples use `ag_7Qb3nT1xK9wZs2Pv0Lm4Rd`.

### Find the endpoint

The card sits at `/.well-known/agent-card/{publicId}.json` on the API host. Its `supportedInterfaces` holds one entry, and that entry is the endpoint:

```json
{
  "url": "https://api.radioso.ai/a2a/ag_7Qb3nT1xK9wZs2Pv0Lm4Rd",
  "protocolBinding": "JSONRPC",
  "protocolVersion": "1.0"
}
```

An A2A SDK reads this itself from the card URL. You only need the endpoint when you call it by hand. The card also lists the skills the agent offers: `ask_agent` for a plain message, then one skill per exposed routine. See [Publish and open an agent](/guides/publish-an-agent#where-an-agent-publishes-itself) for the whole card.

### Send a message

Every request is a `POST` of a JSON-RPC 2.0 body to the endpoint with `Content-Type: application/json` and an `A2A-Version: 1.0` header. A client that can't set headers puts `?A2A-Version=1.0` on the endpoint URL instead; when a request carries both, the header counts. A request that names no version, or any other value, fails with `-32009`.

Access works as it does over MCP:

- **Walk-in.** When the operator turns on **Allow connecting without a credential**, send no `Authorization` header. Opening a conversation draws on the [walk-in budgets](/guides/publish-an-agent#the-budget), which MCP and A2A callers share.
- **Access grant.** When open access is off, or when you want a caller the operator chose, send the grant an operator creates for the agent under **Channels → MCP** as `Authorization: Bearer <secret>`. The card declares it as the `bearer` scheme in `securitySchemes`, and lists it under `securityRequirements` when open access is off. A walk-in refusal tells the caller no more than the card does.

A first message looks like this:

```bash
curl https://api.radioso.ai/a2a/ag_7Qb3nT1xK9wZs2Pv0Lm4Rd \
  -H 'Content-Type: application/json' \
  -H 'A2A-Version: 1.0' \
  -d '{
    "jsonrpc": "2.0",
    "id": 1,
    "method": "SendMessage",
    "params": {
      "message": {
        "messageId": "4f0c1a52-9e0b-4b8e-a7a5-0d6f0f6f2a10",
        "role": "ROLE_USER",
        "parts": [{ "text": "How long do I have to return an order?" }]
      }
    }
  }'
```

A plain answer comes back as a `message`:

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "message": {
      "messageId": "b81d6c0e-2f4a-4c77-9f0e-3f2d5a7c1e44",
      "contextId": "Zk3xQm…",
      "role": "ROLE_AGENT",
      "parts": [{ "text": "You can return an order within 30 days of delivery." }]
    }
  }
}
```

Message parts are text only: `{ "text": "…" }`. A file, raw, URL, or data part fails with `-32005`, and a JSON-RPC batch fails with `-32600`.

### Reuse the `contextId`

The reply carries a `contextId`. Send it back as `message.contextId` on every later message in the same conversation. A send without one opens a new conversation, counts it on the workspace's conversation quota, and draws one from the walk-in budget, so a client that drops the `contextId` gets a fresh conversation per question. That is fine for a single question and wrong for a booking.

Treat the `contextId` as opaque, and as the key to the conversation: for a walk-in caller it is the only thing that continues it. A walk-in context lasts 12 hours. A context opened with an access grant lasts as long as that grant stays valid. If the operator rotates the public id, turns open access off, or revokes the grant, the next request in the context fails. A `contextId` the server cannot continue, whether expired, unknown, or issued to someone else, answers `-32602` with reason `CONTEXT_NOT_FOUND`; start again without one.

### Messages and tasks

A reply is a `message` when the agent answered and nothing else is in flight. It is a `task` when the turn started or continued a routine, when a person owns the conversation, or when a person wrote something you have not seen yet. A task carries a `taskId`, the `contextId`, and a `status.state`:

| State | What it means | What to do |
|---|---|---|
| `TASK_STATE_INPUT_REQUIRED` | The agent is waiting for you. `status.message` is its question, or the reply a person wrote. | Send the answer with the `taskId`, or with just the `contextId`. |
| `TASK_STATE_WORKING` | A person owns the conversation, or a routine waits for an operator's decision. `status.message` is the turn's reply, if there was one. | Poll `GetTask`. The wait has no upper bound. |
| `TASK_STATE_COMPLETED` | The routine finished and its final reply is the task's artifact, or a person handed the conversation back to the agent. | Continue the conversation with a new message. |
| `TASK_STATE_CANCELED` | The routine ended before it finished, for example because it expired after 30 minutes without an answer (reason `routine_ended`), or another routine replaced it (reason `routine_replaced`). `status.message` is the reply to your message. | Read the reply; a new task opens when the next routine starts. |

A2A's task status has no reason field. With the [Radioso converse extension](/reference/a2a-converse-extension/v1) activated, the reason is in `metadata["https://docs.radioso.ai/reference/a2a-converse-extension/v1"].reason`.

A routine that needs an email address and a date, for example, answers the first message with an input-required task:

```json
{
  "jsonrpc": "2.0",
  "id": 2,
  "result": {
    "task": {
      "id": "8e1b0c3a5d94…",
      "contextId": "Zk3xQm…",
      "status": {
        "state": "TASK_STATE_INPUT_REQUIRED",
        "message": {
          "messageId": "1c5a9d20-6b7e-4f43-8a11-7d0e2b9c3f68",
          "role": "ROLE_AGENT",
          "parts": [{ "text": "Which email address should I send the booking to?" }]
        },
        "timestamp": "2026-11-09T10:14:02.117Z"
      }
    }
  }
}
```

A context holds one open task at a time. A message that starts a different routine ends the open task as `TASK_STATE_CANCELED` and opens a new one; the response is the task the turn ended in. A message addressed to a task that has already ended fails with `-32004`.

### Poll a task

`GetTask` with `{ "id": "<taskId>" }` returns the task's current state and its history, which holds only that task's messages. Caller messages are `ROLE_USER`; agent replies and a person's replies are both `ROLE_AGENT`. After a `TASK_STATE_WORKING` response, poll `GetTask`. When a person replies in the Inbox, the next poll returns `TASK_STATE_INPUT_REQUIRED` with their reply as the status message, without you sending anything. A person who replies after a walk-in context's 12 hours cannot reach the caller.

`ListTasks` returns the tasks of one context, newest first, and needs `contextId` in its params. Called without one it returns an empty list. It never crosses contexts.

### Retry a message

A repeated `messageId` in the same context returns the original result and runs no second turn, so a client that did not see the first response can send it again. Pick the `messageId` once per message and keep it across retries. A message sent without a `contextId` is the exception: each attempt opens its own conversation, so a retry of it opens a second one. If the first attempt is still running, the retry answers reason `TURN_IN_PROGRESS`. Send one message at a time per context: a second message that arrives while a turn runs supersedes the first, which answers reason `TURN_SUPERSEDED`.

### What the endpoint does not offer

- **Streaming and push notifications.** The card sets `capabilities.streaming` and `capabilities.pushNotifications` to `false`. `SendStreamingMessage` and `SubscribeToTask` fail with `-32004`, and the push-notification config methods fail with `-32003`. `SendMessage` returns when the turn finishes, and a client waiting on a person polls `GetTask`.
- **Cancelling a task.** `CancelTask` fails with `-32002` for a task that exists and `-32001` for one that does not.
- **The extended agent card.** `GetExtendedAgentCard` fails with `-32004`.

A request over a rate limit gets HTTP `429` with `Retry-After` and the `RateLimit-*` headers before any JSON-RPC handling. Errors carry a `google.rpc.ErrorInfo` entry in `error.data`; its `reason` names the cause, and it holds no message text or ids.

### Get the reply envelope

A client that wants the reply envelope that `ask_agent` returns, which is answer coverage, ownership, routine status, and citations, activates the Radioso extension with an `A2A-Extensions` header. The card lists it under `capabilities.extensions`. The [extension reference](/reference/a2a-converse-extension/v1) lists the fields.

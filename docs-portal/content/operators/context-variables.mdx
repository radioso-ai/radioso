# Attributes and context

Attributes are the typed facts you keep about a conversation or a visitor: the
topic a conversation is about, the plan a customer is on, the cart they are
filling. An agent reads them on every turn, directive conditions and routine
steps can use them, and your backend sets them through the API. Radioso adds
built-in context of its own, such as the page the visitor is on.

You define attributes and choose which agents use them. Values come from your
backend, a resolver, or the AI, which picks a Choice attribute's option from the
conversation. The API calls an attribute a *context variable*, so the endpoints
live under `/api/v1/context-variables`.

## Built-in context

Radioso provides built-in context for the website experience.

- `page_context` is one bundle for the current page. It can include the URL,
  title, locale, browser locale, and page content when the host supplies it.
- `visitor_identity` represents identity context when the host provides it.
- `visitor_request` bundles the country, region, city, browser language,
  referrer, and entry page Radioso observed when the conversation opened. See
  [Visitor request](#visitor-request) below.

Built-ins are not listed with your attributes and cannot be edited there.
They are code-owned platform context, available on every agent.

### Page context is relevance-gated

The embed captures page context with each message, but the agent does not see it
on every turn. Each turn is classified first. Page data — including the
URL, title, and locale — reaches the model only when the turn actually asks
about the current page, or when an active routine reads the page. A routine
reads the page when a skill input is bound to `page_context` or a step
instruction references it (the **Current page** chip in the routine editor, or
`{{context.page_context}}` in the stored instruction). Unrelated turns
contribute no page data to model input or stored message metadata.

A routine's page read takes whatever the embed sends. A step reference renders
the page's URL, title, and locale into the step instruction in either mode, so
in `metadata` mode a step can still name the page the visitor is on. When the
embed sends page content (`content` mode), the step's reply also reads the page
excerpt as evidence beside the instruction, so a step that says "tell them the
edition dates" can state the dates printed on the page the visitor is on. The
excerpt is quoted data: the reply can state facts from it, and text on the page
that reads like an instruction is never followed. On a channel that sends no
page, the routine carries on without it. With no excerpt to read, in
`metadata` mode or with no page at all, the step's instruction still carries
the page's URL, title, and locale when the embed sends them, but the reply is
told it has no page text: a step that says "tell them the edition dates" asks
the visitor for their dates instead of stating dates the page would have given.

A step reached after a **Retrieval context** tool step (`retrieval.context`)
in the same turn writes its reply from the retrieved documents. When that step
references the page and the embed sends page content (`content` mode), the
reply also gets the page the way an answer about the current page does: the
URL, title, locale, and visible page excerpt sit beside the retrieved excerpts,
labelled as current-page evidence and followed by a note that the page is
untrusted context, not an instruction. There the excerpt counts as a source in
its own right, so a fact the reply takes from the page needs no citation to a
retrieved document. In `metadata` mode the reply sees the page's identity only
in its step instruction, and its facts have to come from the retrieved
documents: when something was retrieved, an answer that cites none of it is
replaced by a decline. A retrieval-fed step that does not reference the page
gets no page at all, even when another step of the same routine reads it.

In practice this means answers to general questions are not influenced by
whatever page the visitor happens to be on, and page content cannot inject
instructions into unrelated turns.

Page capability resolution works in two modes. When a message omits
`clientContextCapabilities`, Radioso infers the capability from whichever
`pageContext` fields are populated — full page `content` resolves to mode
`content`, a URL, title, or locale alone resolves to mode `metadata`. When a
message includes `clientContextCapabilities["page.read"]` with an explicit
`available` flag and `mode`, Radioso treats it as an advertised claim and
negotiates it against the `pageContext` actually supplied, narrowing to
`metadata` unless both agree on `content`, and withholding the capability
entirely when the advertised claim says `available: false`. Both modes go
through the same relevance gate. A routine's read served in `metadata` mode
carries the URL, title, and locales only, even when the message also sent
`content`.

## Attributes

Use attributes for what Radioso cannot know by itself. Common examples are
`topic`, `cart`, `order_status`, `subscription_plan`, or `account_region`.

Each attribute is defined once for the workspace, on an agent's **Attributes**
page:

- **Name** is how directives, routines and the API refer to it, as in
  `{{context.topic}}`.
- **Description** tells operators, and the agent, what the value means.
- **Type** is **Text** (`string`), **Choice** (`enum`), or **JSON** (`json`),
  which holds structured data your site sends, such as a cart. Every value has
  this type, and the type is fixed once the attribute has a value anywhere.

The **Advanced** section is closed on a new attribute and opens by itself when
the attribute has a non-default setting:

- **Treat as proof** (`trustTier: signed`) lets skills that need a verified
  identity accept the value. Radioso does not check a signature on the value
  itself, so tick it only when your server alone sets it, such as the
  customer's plan. Unchecked (`trustTier: unverified`), the value is a hint.
- **Private data** (`sensitivity: sensitive`) masks the value in logs, stored
  history and directive conditions, which see `[redacted]`. It does not hide
  the value from replies: wherever an agent's **Used by** is "Every reply, and
  rules, routines and skills", the agent still reads the raw value. Set the
  agent's **Used by** to another option to keep it out of the reply.
- **Used by (default)** (`defaultSurfacing`) is the setting each agent starts
  with. Each agent sets its own **Used by** on its card. The options are "Every
  reply, and rules, routines and skills" (`always`), "Only rules, routines and
  skills that name it" (`on_reference`), and "Only your team"
  (`operator_only`).

A definition is shared: an edit applies at once to every agent that uses it,
published versions included. Each agent then enables the attributes it should
use. On the agent's **Attributes** page, turn an attribute on, then choose **Set by**
and **Used by** for that agent.

The selection belongs to the agent's private draft. Save it, then use **Test
Chat** to try the candidate with sample values for the enabled attributes.
Sample values are private test inputs: publishing the candidate never writes
them as visitor or production values. A Choice sample is the option key.
Changing the selected candidate or sample values starts a fresh test
conversation, so the conversation's context and routine state always match the
version you selected.

When the behavior is ready, review the attribute changes with the other draft
changes and publish the candidate. Definitions and values belong to the
workspace and your backend; the agent revision records which attributes the
agent uses and how it resolves them.

### Choice attributes

A Choice attribute holds one option from a list you write, such as a
conversation's topic with the options Billing, Shipping and Returns. Each
option has:

- **Key**, the identifier a value stores, such as `billing`. Letters, digits
  and underscores, starting with a letter. A key never changes, and two keys
  of one attribute differ by more than case, so `billing` and `Billing` cannot
  both be options.
- **Label**, the name teammates see, such as "Billing".
- **Description**, up to 300 characters on when the option applies, written
  in whatever language your team works in.

An attribute has up to 50 options. To retire one, archive it instead of
deleting it: stored values and filters name options by key, so a key stays
valid for as long as a value holds it. An archived option is no longer accepted
as a new value; a value that already holds it keeps it. Restore the option to
offer it again. At least one option stays active, so the attribute always has a
value it can take.

A value is stored as its key, and a turn reads it by its option. A directive
condition sees both, as `{ "key": "billing", "label": "Billing" }`, so a
condition written in your team's language matches the label. The answer prompt
and a routine step's `{{context.topic}}` show the label. A skill input bound to
the attribute receives the key, the identifier your own systems act on. When
that input is a choice of its own, it has to accept every key of the attribute,
archived ones included, because a value that holds an archived key keeps it.
A routine that binds the attribute to an input missing one of its keys is
refused with `context_variable_option_not_accepted`, naming the missing keys.

**Set by** is where the agent gets the value. The dashboard offers two sources:

- **Your website or API** (`pushed`): the host backend writes values through the
  REST API.
- **The AI, from the conversation** (`classified`): after each reply, the AI picks
  one of a Choice attribute's options from what the visitor wrote. The next
  section covers it.

Resolver-backed attributes exist in the API model. The dashboard does not
configure them.

### The AI, from the conversation

Say you want every support conversation labelled with its topic, so a rule can
route billing questions and your team can see what people ask about. Create a
Choice attribute `topic` with the options Billing, Shipping and Returns, give
each option a description of when it applies, and set the agent's **Set by** to
**The AI, from the conversation**.

After each reply the agent sends, Radioso reads the conversation and picks the
option that describes it, or none when no option fits. It writes the option's key
as the conversation's value (conversation scope), so a visitor who asks "Why was I
charged twice?" gets `topic: billing`. When the conversation moves on, say to a
return, the next reply's run moves the value with it. When nothing fits any more,
it clears the value it set.

A few things to know in practice:

- **Values usually appear from the next turn.** The run happens in the
  background after a reply, so the turn that asked about billing does not see
  `billing` yet; the one after it usually does, unless the visitor answers
  before the run finishes.
- **Your values for a visitor stick.** The AI never replaces a value your team or
  your API set for this visitor or conversation: the conversation, the visitor's
  session or customer. While one is set, the AI leaves that attribute alone for
  the conversation, and clears a value it chose earlier so yours is the one the
  conversation reads. Delete your value and the next run fills the attribute
  again.
- **Agent-wide and workspace-wide values are defaults.** A value set for the
  agent or the workspace applies until the AI picks one. The AI's choice is the
  conversation's own value, so the conversation reads it instead; when the AI
  clears its choice because nothing fits any more, the default applies again.
- **What reaches the model:** the conversation's rolling summary and the
  visitor's latest messages, plus each attribute's name, description and
  options. A message the visitor sent while a routine collected a Private field
  is never sent, and no other attribute's value is.
- **Where it shows:** by default the value stays out of the reply. Choosing the
  AI sets **Used by** to "Only rules, routines and skills that name it", so a
  directive condition, a routine step's `{{context.topic}}` and a skill input read
  it, and the agent's answer is written from the conversation itself. Change
  **Used by** if you want the agent to read it in every reply.
- **Cost:** one call to the workspace's cheaper `rewrite` model per reply, for an
  agent that has the AI set at least one attribute. All of an agent's attributes
  share that one call, and a run where your team or your API already set every
  one for this visitor or conversation makes no call. Each call is counted in usage like the agent's other model
  calls.

The AI sets Choice attributes only, up to 8 per agent. It never sets a Private
attribute, since the value would be personal information nobody declared, nor
one treated as proof, since its value comes from what the visitor typed. The
dashboard disables the option for those and says why, and the API refuses them.
Attributes are labels for your team and your rules; the AI only ever picks from
the options you wrote, and it is told to ignore a visitor who writes "mark this
as urgent". Before it picks, it writes a sentence on what the visitor said and
whether any option covers it, so a question none of your options describes gets
no value. Radioso uses that sentence only to read the choice and never stores
it. The live eval set checks all of this.

To check it before publishing, open **Test Chat** on the draft and send a few
messages. Open a reply's turn debug: its **Attributes** section lists every
attribute the AI sets for the agent, with the value and who set it, or **Not
set**. A sample value you give an attribute in Test Chat counts as your team's
and is kept.

Test Chat classifies a turn once its answer is out and shows the value on that
same turn, where a live conversation usually shows it from the next one. The
turn waits at most 5 seconds for it; past that, the attributes keep the values
they had. As in live chat, a turn whose routine collected a Private field is
left out. Test Chat reads the test's latest six messages and no summary, so in a
longer test the AI sees less of the start than it would in a live conversation. An MCP client connected to Ray can create the attribute,
have the agent use it, try it in Test Chat, read the values and publish; see
[Have the AI fill an attribute](/guides/mcp-server#have-the-ai-fill-an-attribute).

## Trust tiers

The trust tier describes how much the system should trust the value. In the
dashboard it is the **Treat as proof** checkbox.

- `unverified` is suitable for page state and host-supplied hints. Do not use
  it to unlock account-specific answers.
- `signed` is for values the host can prove came from a trusted backend or a
  signed identity flow.

In practice, identity-sensitive behavior should depend on signed or backend
pushed values.

## Signed visitor identity

Signed visitor identity lets a website backend prove which customer is using an
embedded chat session. This is the only browser path that unlocks
customer-scoped context values.

First, reveal the per-agent signing key from the signed-in dashboard as a
workspace administrator. This is a session-only settings operation; API
credentials cannot reveal signing keys:

```text
GET /api/v1/agents/{agentId}/context-variables/signing-key
```

The response contains a hex HMAC key derived for that workspace and agent. It is
not stored as a separate database secret.

Your backend signs this payload:

```json
{
  "customerId": "cus_123",
  "sessionId": "public-session-id",
  "origin": "https://example.com",
  "issuedAt": 1782398400000,
  "nonce": "unique-random-value",
  "attributes": {
    "plan": "pro"
  }
}
```

Create the token as:

```text
payload = base64url(JSON.stringify(payloadObject))
signature = base64url(HMAC_SHA256(signingKeyBytes, payload))
token = payload + "." + signature
```

Pass the token to the launcher with a provider function, or with a string:

```js
window.Radioso.identify(async ({ sessionId, origin }) => {
  const response = await fetch(`/identity?session=${sessionId}`, {
    credentials: 'same-origin',
  })
  const { token } = await response.json()
  return token
})
```

```js
window.Radioso.identify(token)
```

The string form goes out unchanged with every message, and each message's
nonce is single-use, so a static token verifies exactly one message — the
first one that carries it. Radioso records the customer on the conversation
the moment a turn verifies, so later turns keep the `customer` scope even
though the built-in `visitor_identity` value and its `attributes` show up only
on the turn that verified. Use the provider form above for any conversation
with more than one turn.

A provider is the form a website backend should use. The token has to carry
the public chat `sessionId`, and only the embed knows it — the session begins
when the visitor opens the widget, not when the page loads. Verification also
checks a single-use nonce and a five-minute `issuedAt` window on every
message, so the token that always verifies is the one minted at the moment of
use. Minting per message keeps the built-in `visitor_identity` context value,
with the token's `attributes`, present on every turn. A same-origin endpoint
such as `/identity?session=<sessionId>`, called with `credentials:
'same-origin'`, is the typical provider: it reads the host's session cookie,
checks the logged-in visitor, and signs the payload above.

### When the provider runs

Radioso calls the provider right before it sends each visitor message,
passing the chat's current `sessionId` and the host page's `origin`
(`window.location.origin`). The provider returns the token as a string, or as
a `Promise` that resolves to one.

If the provider returns anything else, throws, or takes longer than five
seconds, that message goes out without identity and the turn continues as
anonymous.

Radioso verifies the token on each message. Verification is strict:

- the signature must match the current or previous per-agent signing key
- `issuedAt` must be within the acceptance window, five minutes
- `sessionId` must match the established public chat session
- `origin` must match the approved embed origin
- `nonce` must not have been used before inside the acceptance window
- the token is at most 8,192 characters

If any check fails, the identity is treated as absent. The visitor turn still
continues as anonymous. Radioso does not expose token, payload, or secret values
in logs.

To see why a token was refused, read the `outcome` label on
`radioso_public_chat_identity_verifications_total`. It counts every token a
visitor message carried, under `verified`, `too_long`, `not_configured`,
`malformed`, `invalid_signature`, `invalid_payload`, `expired`, `wrong_session`,
`wrong_origin`, `replayed`, `no_origin` or `error`. `wrong_origin` and
`wrong_session` are the usual signs of a site signing for the wrong page or
session, and `expired` of a clock that has drifted. Each refusal is also
logged with the workspace id, the agent id and the outcome.

When verification succeeds, Radioso adds the `customer` scope to context
resolution:

```text
conversation -> session -> customer -> agent -> workspace
```

It also exposes a sensitive built-in `visitor_identity` context value with
verified trust. Unsigned browser identity never gets verified trust and never
unlocks customer-scoped data.

Token `attributes` are a per-turn hint — good for something true only in this
session, such as the plan the visitor is currently comparing. For a durable
customer fact such as a name, an email address, or order history, push a
`customer`-scoped attribute from the host backend instead: it persists for that
customer across sessions, where `attributes` do not.

## Visitor request

`visitor_request` gives a prompt six facts about the request that opened the
conversation, and gives directive conditions five of them:

- `country`, `region`, `city` — read from the geo header a load balancer or
  CDN stamps on the request, such as Cloudflare's `CF-IPCountry`.
- `language` — the primary tag of the browser's `Accept-Language` header, so
  `de-DE,de;q=0.9` resolves to `de`. Prompts receive it; conditions don't, as
  explained below.
- `referrer` — the page that sent the visitor, reported by the embed launcher.
- `entryPageUrl` — the page the chat opened on, reported by the embed
  launcher.

The IP address and user agent that accompanied the request are not part of
it — `visitor_request` carries only the six fields above, so a directive that
reads it never sees an address or a browser fingerprint. Values are
unverified: they describe what the request looked like, not a proven
identity.

`entryPageUrl` shares its sensitivity with `page_context`, so it follows the
same page-read gate: it reaches `visitor_request` only on a turn where that
turn's own page-content check is open, and drops out otherwise, even though
the conversation opened on that page throughout. The other five fields carry
no page-content sensitivity and reach every turn that has them, regardless of
that turn's page-read decision.

`visitor_request` is available on every agent, the same as `page_context` and
`visitor_identity` — there is no per-agent setting to turn it on. It reaches a
turn whenever the conversation carried at least one of the six facts; a
directive condition such as "when the visitor is in Germany, mention that
shipping to the EU takes 3-5 days" reads `visitor_request.country` the same
way it would read any attribute.

Conditions see every field except `language`. The step that judges conditions
also picks the language of the reply, and it picks it from the words the
visitor writes, so an Italian question from a browser set to English gets an
Italian answer. Conditions see only the fields the request carried, and a
`visitor_request` whose only fact is `language` is left out of condition
matching altogether.

## Surfacing

Surfacing is the **Used by** setting in the dashboard. It controls whether a resolved value is shown to the model as part of
the prompt context.

- `always` includes the value in the answer prompt whenever it resolves, and
  leaves it available to directives, routine steps and skill inputs.
- `on_reference` keeps the value out of the answer prompt. Directives, routine
  steps (`{{context.x}}`) and skill inputs that name it read it.
- `operator_only` stores it for operator inspection and logic, but does not
  surface it into the answer prompt; a routine step that references it reads
  nothing.

Private data (`sensitive`) is masked in logs and history, not in the answer
prompt when surfacing is `always`, so use the narrowest surfacing that works. Redacted
values may still appear in the Inbox so operators can debug what happened
without exposing raw sensitive data.

## Conditions that read context

Directive conditions are judged against the turn's visitor context, so a
condition can describe visitor state rather than only what the visitor said.
"The visitor's cart is worth more than 100" or "the visitor is on a product
page" are conditions the matcher can decide, because `cart` and `page_context`
are part of the signals it sees.

Alongside your own attributes, the turn carries one fact Radioso establishes
itself: `radioso_caller_kind` is `agent` when the other side of the conversation
is another AI agent rather than a person, and `human` otherwise. Radioso reads it
from the channel the conversation arrived on — the MCP converse door and the REST
agent channel carry agents; the embed, a shared link, Slack, and the dashboard
carry people — so a caller cannot claim to be something it is not. Write
"the caller is another AI agent" to scope a directive to them, which is how you
give agent callers a terser answer or a different escalation path than a person
gets. The key is present on every turn, so a condition about it always has
something to read.

Test Chat and the workbench run as `human`, because an operator driving a test is
a person. A condition scoped to agent callers is therefore one you confirm
against real traffic from the MCP converse door or the REST agent channel rather
than in a test run.

Every resolved attribute takes part, whatever its surfacing: `operator_only` and
`on_reference` values steer behavior without being written into the answer
prompt. Two limits are worth knowing when you write a condition:

- Sensitive values arrive as `[redacted]`, so a condition that depends on
  reading one cannot hold. Condition on a non-sensitive companion value instead
  — an `account_tier` string rather than the account number.
- Long values are shortened and a turn's context is capped, so conditions that
  hinge on something deep inside a large JSON blob are unreliable. Push the fact
  the condition needs as its own attribute.

Page context reaches conditions as the URL and title. The visible page excerpt
and the page and browser locales are not part of it, for the same reason
`visitor_request.language` is left out: the reply language follows the words
the visitor writes. A condition about which language version of a site the
visitor is on can read the URL.

## Pushing values

A host backend sets a value with:

```text
PUT /api/v1/context-variables/{id}/values
```

The body names a scope and the value. To label one conversation, on any
channel, use its conversation id:

```json
{
  "scope": { "type": "conversation", "id": "3f2b8c1e-6a4d-4f0e-9b7a-2c5d8e1f4a60" },
  "data": "billing"
}
```

A Choice value is the key of an active option; a Text value is a string; a
JSON value is any JSON, such as a cart:

```json
{
  "scope": { "type": "session", "id": "public-session-id" },
  "data": {
    "items": [
      { "sku": "course-101", "quantity": 1 }
    ]
  }
}
```

Radioso resolves values from most specific to least specific:

1. `conversation`
2. `session`
3. `customer`
4. `agent`
5. `workspace`

Use conversation scope for a fact about one conversation, such as its topic.
Every channel has it, and the id must name a conversation of the workspace, or
the call returns `404`. Use session scope for short-lived visitor state on the
website, customer scope for account data, agent scope for agent-specific
defaults, and workspace scope for shared defaults.

### Who set a value

Every value records its last writer. The response, and a later
`GET /api/v1/context-variables/{id}/values`, carries it as `writtenBy`:

```json
{
  "writtenBy": { "kind": "api", "ref": "7d1c2b9e-0f4a-4c3e-8a6b-5e9d2f1c4b70" }
}
```

A value set through this API has `kind` `api`. `ref` is the id of the API
credential that made the call, or the teammate's user id when a dashboard
session did. A value a resolver cached, or one stored before writers were
recorded, reads as `api` with a `ref` of `null`. A value the AI set has `kind`
`classifier`, and its `ref` names the version of the instructions it was chosen
with, such as `context-classification/1`.

Conversation-scope values are deleted with their conversation, and a data
subject export lists them with the kind of writer that set each one.

## Inbox

Open a conversation in the Inbox and inspect the assistant turn. When
attributes were resolved for that turn, the debug panel shows a read-only
**Visitor context** block. Sensitive values are already redacted by the backend
before they reach the dashboard.

# Retrieval pipeline

Retrieval is one of the core pipelines an agent can use. Behind a single question sits a staged pipeline that turns a user message into evidence, assembles a prompt, and presents an answer with citations.

The stages matter because they are where quality goes wrong. When an answer is off, find the stage that failed before you start changing agent skill settings, ingestion settings, or prompts.

## Stages

<Steps>
### Retrieval context

The pipeline starts by resolving system retrieval defaults, any `retrieval.answer` skill settings on the selected agent, and a limited conversation window. This stage decides the behavioral frame for the turn before any search runs.

### Query interpretation

Radioso parses the original query, applies rewrite logic when enabled, and can split the request into retrieval subqueries. This is where semantic and lexical rewrite instructions matter.

A follow-up such as "send me a quote for the event" names no subject of its own. Interpretation resolves it to the subject the visitor named earlier in the conversation, even when the agent's last turn only asked for a name and email. When the rewritten queries leave that subject out, retrieval adds it: every semantic query names it, and a lexical search for the subject alone runs beside the lexical searches the model wrote. Lexical search counts a chunk that holds part of a query only as support for other evidence, so the subject runs as its own search, where the subject's own pages hold every term. This applies to follow-ups and to questions that relate an earlier subject to something else, on turns with conversation history.

The query interpretation stage of the turn trace shows the resolved subject, the related entities, and the one-line resolution note. `subjectAnchored` is `true` when retrieval added the subject itself, and `anchoredSubject` shows the text it added.

### Candidate retrieval

The system runs semantic and lexical retrieval. Semantic retrieval uses embeddings. Lexical retrieval uses search text built from the document title, chunk content, and metadata-derived text.

Lexical search looks for chunks that hold every query term first. When fewer than 3 chunks hold them all, it also looks for chunks that hold part of the query, and returns them after the full matches. The lexical query `preventivo completo pernottamento evento` mixes request words with subject words, so no page holds all four; the course page holding `pernottamento` and `evento` is still found. The partial matches follow these rules:

- A rarer term weighs more. Each term weighs ln(N / n), where N is the number of the agent's searchable chunks (counted up to 10,000) and n is the number that hold the term, so a word on most pages counts least, in any language. A term no chunk holds weighs nothing, so an English question over an Italian corpus is measured by the words the corpus shares with it. A term held by more than 200 chunks weighs nothing either, and cannot find a chunk on its own.
- A chunk holds at least a third of the weight of the query's weighted terms, and at least as much weight as one term held by a tenth of the chunks. A page sharing only the query's frequent words stays out, even when a frequent word is the only one the workspace holds. Among the rest, the chunk holding more weight comes first, and PostgreSQL's `ts_rank_cd` over the terms it holds breaks ties.
- Two adjacent words also match as one: `super coscienti` finds a page that writes `Supercoscienti`. That page holds neither word as written, so it is a partial match.
- Quoted phrases count as one term each, and excluded terms stay excluded. Punctuation and search operators in the query separate words; they never act as operators.
- A chunk is scored on the query's 12 rarest weighted terms, out of at most 32, and the search ranks at most 1,000 chunks, taken from its rarest terms first.
- The partial-match search gets 150 ms, counting and ranking together, and is skipped while other requests wait for a database connection. When it is skipped, runs out of time, or fails, lexical search returns its full matches.

The lexical stage of the trace records what the partial-match search did as `someTermsPass` (`skipped`, `ran`, `timed_out`, or `failed`), with `someTermsPassSkipReason` when it was skipped, `someTermsPassDurationMs`, and `someTermsCandidateCount`. Each chunk the stage lists carries `lexicalTermCoverage`: `all_terms` or `some_terms`. The reasoning retrieval strategy's `lexical_search` tool returns full matches only.

The two run concurrently. Lexical queries go out before the query embedding resolves, so lexical results are often already in hand when vector search starts.

The pipeline also asks a retrieval-owned temporal candidate port for chunks by their `dateFrom` and `dateTo` metadata. When the question names a date or period, the query rewrite returns it as an inclusive `requestedDateRange` (ISO dates, resolved against today's date in UTC), and the port returns the chunks whose dates overlap that range, whatever shape or temporal mode the rewrite gave the question. Within the range, chunks closest to the question's embedding come first, from an exact sort over the range's chunks with no similarity threshold, and each event's first chunk comes ahead of any event's later chunks; without an embedding, the range comes soonest first. A listing question with no range gets ongoing and upcoming chunks, soonest first. This path is controlled by the agent's temporal structured lookup setting, and the retrieval trace's temporal stage records the range it used.

### Candidate preparation

Retrieved chunks are normalized, merged, and scored. Metadata rules and explicit metadata filters narrow or boost the candidate set here.

Semantic cosine and query-relative lexical scores stay separate. Candidate preparation combines their source ranks into a fused score from 0 to 1, with a bounded boost when both sources find the same chunk.

Two lexical gates apply, and they answer different questions. Fusion ranks candidates against each other, so it gates on the query-relative lexical score: a chunk contributes its lexical rank once it reaches 0.2 against the best lexical hit for that query. Evidence checks — trigger backoff and minimum-useful-candidate counts — ask whether the turn found real lexical signal at all, so they gate on the absolute PostgreSQL `ts_rank_cd` value against a floor of 0.05. A rare-term query can produce top hits whose absolute rank sits well under that floor. Those hits rank normally against their peers, and they count as thin evidence.

A partial lexical match supports other evidence. Its lexical rank enters fusion as the secondary source only, so it lifts a chunk that semantic search also found, and on its own it ranks below semantic hits. It never counts as lexical evidence in those checks, and a definition lookup's preference for lexical hits passes it over. A turn whose only candidates are partial lexical matches keeps none of them, and answers as a turn that found no evidence.

When upcoming-event boost is enabled, dated event evidence can receive a temporal boost during event date lookups: evidence in the requested range when the question names one, otherwise ongoing and upcoming evidence. Topic relevance still applies; the temporal signal refines the candidate set rather than replacing it.

### Context selection

The system reranks candidates when reranking is enabled, then selects the final prompt contexts. `vectorTopK`, `similarityThreshold`, `rerankEnabled`, and `rerankTopK` all influence this stage, but only the top candidates `rerankTopK` keeps (at least 12, never more than 50) reach that selection — the final answer uses up to 12 passages, at most 2 per document. When temporal structured lookup finds passages in the period a question names, the answer is composed from two groups: up to 4 of the best undated candidates outside the period, then the period's most relevant passages, at most 2 per document, up to 20 passages in all and inside the prompt's context token budget. The reserve keeps the page that answers a question which only mentions a period, such as a cancellation policy, from being crowded out by the period's events — a candidate dated to a different period never takes one of those 4 slots. A period with few passages is filled to 12 from the candidates outside it instead, dated to another period or not. The selected passages are then put in date order for the prompt.

When deterministic temporal sort is enabled, selected dated event contexts are ordered by their dates before prompt assembly, with contexts in the requested range first when the question names one, whatever its shape. This makes "next events", "what's on next weekend", and "sort by actuality" evidence order stable.

### Prompt assembly and diagnostics

Radioso builds the final prompt, generates citations, and captures diagnostics and a retrieval trace. The prompt carries today's date with its weekday, and, when the question names a period, a requested-period line in the answer request that asks the model to answer for that period. Chat then uses that result to generate the answer.

Each retrieval branch is timed around its own work, so the trace shows the semantic and lexical spans as they actually ran. Read them as overlapping: the two stages can start at different moments, and because they run concurrently their durations can add up to more than the retrieval stage that contains them.
</Steps>

## What operators can adjust

Retrieval behavior is configured per agent through the `retrieval.answer` skill. Retrieval-only API calls use system defaults and still accept per-call controls such as `metadataFilter`.

- `retrievalStrategy` controls the execution style. `fixed` runs one search pass, `reasoning` lets the model plan and run multiple searches, and `auto` lets Radioso choose per query.
- `vectorTopK` controls how many chunks are fetched from the vector index before filtering and reranking. After filters, boosts, and merging, only the top `rerankTopK` candidates (at least 12) go on to the answer, so a deeper fetch matters when filters or boosts lift lower-ranked chunks into that group.
- `rerankEnabled` controls whether fetched chunks are re-scored with the reranker model. It is off by default.
- `rerankTopK` controls how many top candidates go on to the answer, reordered by the reranker when it's enabled. Values below 12 act as 12; the max is 50. The answer itself still uses up to 12 passages, at most 2 per document. When temporal structured lookup finds passages in the period a question names, the answer holds up to 20: those passages plus up to 4 of the best-matching undated candidates from outside the period. A candidate dated to a different period fills in only when the period itself is sparse.
- `citationHoldEnabled` controls whether the answer is held until it earns its first citation before it streams. It is on by default; when off, an answer that ends with zero sourced claims still reaches the visitor and is flagged degraded in Quality.
- `queryRewriteEnabled` controls whether the user message is rewritten into search queries before retrieval.
- `semanticRewriteInstructions` replaces the default instructions for rewriting the semantic vector search query. Empty means the default applies.
- `lexicalRewriteInstructions` replaces the default instructions for rewriting the lexical keyword search query. Empty means the default applies.
- `suggestedQuestionsEnabled` controls whether follow-up question suggestions are offered after each answer.
- `suggestedQuestionsCount` controls how many follow-up questions to suggest.
- `metadataRules` constrain the candidate set before prompt assembly for the agent.
- `temporalStructuredLookupEnabled`, `temporalBoostUpcomingEnabled`, and `temporalDeterministicSortEnabled` control date-aware event lookup, boosting, and ordering for the agent.
- Per-request `metadataFilter` constrains retrieval API calls without changing saved agent settings.
- `customInstruction` influences how the final answer is written, but it cannot rescue bad retrieval.

## What happens after retrieval

Retrieval does not directly become the user-visible answer. The agent chat layer presents the model output as answer segments with citations derived from the retrieved evidence.

<Callout type="info" emoji="i">
  In practice, poor answers usually come from weak retrieval inputs, weak candidate selection, or overly aggressive filtering. Prompt tweaking should usually come after you verify those earlier stages.
</Callout>

## Debugging order

1. Confirm the document was fully processed and chunked.
2. Check whether the query needed rewriting or metadata filters.
3. Increase candidate depth before strengthening retrieval signals.
4. Revisit `customInstruction` only after retrieval evidence looks correct.
